## Muse — 2026-10-24 08:27

先说结论：你现在的用法没错，但你走的恰好是整条链路里最脆的一条。全网 + 官方 Discord 的检索我已经单独派出去查了（有没有人遇到同题问题、官方有没有回应、双指长按和 Agent 互跳的官方说法），结果回来我再补一份带出处的；在那之前，先把问题本身和两个方案拆透。

**一、先核实：你的用法对不对，错在哪一层**

你记录下来的真机流程就是「乐奇，打开 xxx 智能体」，官方侧也对得上：`乐奇` 是官方中文唤醒词，运行时文档里唤醒来源就三个——`乐奇`、`Hi Rokid`、触控唤醒 `clickAiAssist`。所以用法没错。

但要看清这条链的结构：唤醒 → **宿主** ASR → **宿主**按名字做意图匹配 → 拉起 Agent。这是三段串联，成功率是相乘的，而且全程发生在 Agent 代码运行之前。也就是说：

- 「打开…智能体」被听错，是宿主的识别问题；
- 名字发音稍偏不命中，是宿主的匹配问题（官方文档里我没找到任何别名、同音容错、模糊匹配的配置项，`app.json` 里根本没有 intent/别名字段）；
- 这两个问题，**Agent 自己一行代码都救不了**——它还没被打开呢。

这决定了两个方案的性质不同：方案一是在宿主规则内把输入变简单；方案二是换一条不经过宿主名字匹配的入口。

还有一个先要做的诊断，别急着改名：下次失败时留意 AI 对话界面显示的识别文字，分三类——① 识别文字就错了（ASR 问题）；② 文字完全正确但没打开（匹配/资源包问题，改名帮助有限）；③ 名字对、坏在「智能体」三个字上。尤其第③类有个零成本试验：**「智能体」这个后缀很可能不是必须的**。试「打开厨伴」「厨伴」「启动厨伴」「用厨伴查过敏原」几种说法各三次，如果裸名字就能命中，你的失败率当场就少一段最容易出错的载体词，不用动任何 Agent。

**二、方案一：三字符短码名**

方向对，但有三个坑，第一个是字母表本身：

- **最直觉的字母恰好最危险。** 英文字母名里 B/C/D/E/G/P/T/V/Z 全押 -ee 韵，听感几乎是一家人，必须整组排除；I 和 1、O 和 0 互撞排除；M/N 只留一个（留 M）；A/J 与 K 同韵且 A 撞 8，排除 A/J；S 与 F/X 在 es/ef/eks 上成团，排除 S；U/W 转写不稳定排除。
- 剩下的安全池大约是 **F、K、L、M、Q、R、X、Y** 这 8 个——音节彼此拉得最开。数字放中间做分隔（字母-数字-字母），比尾随数字更好切分。8×10×8 = 640 个组合，扣掉重复字母、常见缩写（像 KFC 这种会被 ASR「纠正」成词的），还够 120 个 Agent 用绰绰有余。第一位还可以固定编码系列（指向性/注意力/路缘坡各占一位），短码就不是纯随机串，记忆负担小很多。
- 数字读法要先定死一种：英文 seven 还是中文「七」，混读是识别大忌。中文电信式读法（幺、拐、勾、洞）虽是为防混设计的，但宿主转写的是数字字符本身，用不上。

第二个坑是**名字有两层，可能拆不开**：Studio 里的名字既是货架上的显示名，又大概率是唯一的唤起名。把显示名改成 K7M，用户（包括提审）看到的就全是密码串——提审规则对名字只有 ≤20 字符之类的限制，纯编码名能不能过审、影不影响商店可发现性，都是未知数。所以先拿一个 Agent 做三选一试验再决定：① 改纯短码名，看能否叫开、提审口径如何；② 复合名「语义名+短码」，看只说短码能否命中；③ 语义名不动，只在 Intent Description 里写短码，看宿主会不会按短码路由。结果不同，方案一的形态完全不同。

第三个坑是它只治个人机队：你这 120 个 Agent 本来是当产品生产的，短码对你自己是索引，对其他用户是记忆灾难。短码更适合做**你的机队别名层**，而不是产品的正式名字——前提还是上面那个拆分试验。

**三、方案二：Agent 路由**

这个方案的上限明显更高，因为它把「一次说对」换成了「确定性选择」，但它有一个生死问题，我先把好话和坏话都说完。

好的部分，一旦进了路由，规则全是我们的：

- 宿主 ASR 在路由**内部**完全是另一道题：候选集是封闭的（你的收藏清单就那么些），官方 ASR 会话还支持 `phrases` 热词加权，可以把清单名字全喂成热词；转写回来我们自己做拼音/编辑距离模糊匹配，听错一两个音也能落回正确候选；再加 TTS 读回 + 点头确认（点头是官方手势）兜底。不是引擎变好了，是判卷标准变成我们的了。
- 语音只剩裸名字、甚至只说短码，不再需要「打开…智能体」。
- 滑动选单是确定性输入，不依赖识别——前提是前后滑镜腿的事件映射要实测（文档里镜腿侧是 ArrowUp/Down、Enter、Backspace 和 GlobalHook 这套键事件）。

坏的部分，也是必须先验证的两点：

1. **入口绑定的前提待核实。** 官方产品页只有一句 "Quick Action Shortcuts — Tap to launch the features you use most"；「双指长按绑自定义 Agent」这个具体说法不在我们审过的官方档案里，它以你眼镜/手机 App 设置里实际能选的为准。如果那个槽位只有一个，把它给路由而不是给某个具体 Agent，是对稀缺硬件入口的正确分配——这一点我完全同意你。
2. **Agent 能不能打开另一个 Agent，官方文档里没有这个 API。** 我核过框架和 window 的全部契约：`window.open` 只能开自己 `app.json` 里声明的 Widget，不能跳到别的 Agent。如果最终确认平台真没有互跳机制，路由的形态会降级为：选中目标 → 大字显示短码 + TTS 念出标准读法 → 你退出后只说短码。它仍比现状强（硬件入口 100% 可靠 + 只剩 3 字符要说），但不是一键直达。这一条和 Discord 那边有没有人问过，是我这次检索的重点之一。

另外路由有个小问题要提前设计：AIUI 没有「枚举本机已装 Agent」的 API，收藏清单只能由我们自带注册表（你这 120 个 Agent 本来就全是我们生产的，把 PLAN 清单做成路由内置注册表反而是优势），localStorage 记收藏顺序和最近使用。120 个全靠滑动翻是灾难，首页必须是收藏+最近（≤8 个），其余按组分页，短码/语音做快速定位。

**四、我的建议：不是二选一，是三层叠起来**
主入口走路由（硬件唤起），短码作全机队统一别名层（路由内直达 + 路由外兜底直呼），语义名保留给商店、README 和提审。顺序上，先做四个廉价试验再动任何量产管线：

1. 失败样本分类 + 去后缀说法试验（今天就能做，零开发）；
2. 短码字母表实测：安全池 10 个码 vs 被排除字母 10 个码，你本人各读三遍喂宿主 ASR，比转写准确率——字母表让你的嗓子投票，不让理论投票；
3. 用 glasses-benchmark 现成的交互监听项当探针：双指长按、前后滑到底给的是什么事件码，顺带试那个槽位能不能绑调试版 Agent；
4. 互跳机制：等检索结果 + 必要时拿这个问题去问官方（措辞我来起草，你点头再发）。

- 唤醒事件 `onVoiceWakeup` 的已知来源就三个：`乐奇`、`Hi Rokid`、触控唤醒 `clickAiAssist`。官方明确建议：**默认不要按 `event.keyword` 过滤**，事件一触发就直接进入语音交互；只有当你想接管宿主默认动作时才 `preventDefault()`。[PR #50 原文](https://github.com/yodaos-project/AIUI/pull/50)
- 同一文档最后还有一句容易被忽略的：把唤醒和手势回调当作**可选信号**，产品需要时应**保留另一条可用的交互路径**。换句话说，官方自己的口径就是「别把语音唤醒当唯一入口」——你用触控板长按做确定性入口，恰好是照着官方这条建议在做。

**2. 用户说明书层——只教唤醒助手，不教唤智能体**
官方说明书（User Manual V2.1）的教法是：说 "Hi, Rokid" 唤醒 AI 语音助手，然后直接说功能命令，示例全是拍照、录像、录音、看看我前面有什么这类**内置功能**。「打开某某智能体」这种说法格式，官方任何文档里都没有给出过——它不是一条有文档背书的命令语法，更像是助手对话流的自然语言习惯，所以也就没有命中规则可查。

**3. 提审层——只有合规，没有识别友好性**
名字 ≤20 字符、不重名、不含测试/促销词，这些是商店审核口径，跟「名字好不好被 ASR 听准」无关。官方没有 invocation name（唤起别名）这种机制，也没给过任何命名建议：避同音、避生僻发音、用短名，一个字都没提。

**完全空白的部分**（这次我又复查了一轮，确认还是没有）：别名/同音容错怎么配、宿主按名字匹配的规则是什么、Intent Description 该怎么写才利于路由、唤不出来怎么排查、命中率是多少——全部没有。最贴边的官方仓库记录还是 issue #38：开发者要求「经 AI 助手唤起的 Agent 能拿到当时的对话上下文好调试」，至今 open 未实现，等于官方侧连诊断入口都没给。[issue #38](https://github.com/yodaos-project/AIUI/issues/38)

所以结论是：短码和触控路由这两条路都没有违背任何官方指导——官方在这一层就是留白的，唯一能引用的官方依据反而是那句「保留语音之外的交互路径」。

**第一层：直接讨论「智能体呼出」的——没有，零条。**

没有任何人在公开渠道原样讨论过「说『打开某某智能体』不命中」「Agent 名字叫不出来」这个问题。逐渠道的结果是：

- **GitHub 官方仓库**：全量清点过 81 条 issue/PR + 7 条 discussion，没有一条谈拉起失败。这是唯一一个能说「确实没有」的地方，因为是全量而不是抽样。
- **Discord / Reddit / X**：以相关关键词检索，公开索引里零命中。Discord 要打折——服务器内容默认不被搜索引擎索引，只能说公开层面看不到，不能断言里面没人聊过。
- **知乎 / B站**：站内定向检索无结果；**小红书**搜到的全是站外开箱文，没有一条原帖；**微信公众号**只有媒体转载，没人谈唤出失败。
- **YouTube**：最接近的是一条评测视频里有个章节叫 "The Voice Command Workaround"，但讲的是语音命令的通用绕法，不是呼智能体。

**第二层：讨论「上一跳」的——很多，而且口径一致。**

大家吐槽的都是唤醒词和语音命令本身不可靠：Gizmodo 说 "Hi Rokid" 基本喊不应、母语者一说就中；PhoneArena 说系统永远把 Rokid 听成 Rocket；Amazon 用户评价里有「唤醒词被认出来了但助手立即退出」「stop/cancel 这种固定命令词不识别」——最后这条和你的故障是同一类：**固定词被 ASR 吃掉**。也有反例，Trusted Reviews 说几乎不误听，说明这事因人、因口音、因环境方差极大。
