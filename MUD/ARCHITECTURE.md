## 0. 一句话定义

玩家站在真实地点拍一张照，眼镜把眼前的场景写成一间 MUD 房间：文字描述、由场景里的东西生成的 NPC 与道具、按拍照那一刻头部朝向定出的东南西北出口。每到一个新地方拍一张，就是一间新房，房间连成的图只属于这个玩家。成长、背包、任务链、NPC 记忆、文字回合制战斗都长在这张真实地图上。

多人是后置阶段的事：本游戏最终是大型多人，但路线是单机先行——第 1、2 阶段纯单机，第 3 阶段才上自建后端做云端存档与异步共享，第 4 阶段才做多人。任何阶段不得为下一阶段在文案里预支能力。

## 1. 立项复核（SOP 三关 + 冲突 + 环境常识）

- **场景关**：玩家在自己日常活动的地方（街道、公园、商场、校园、公司楼下等公共场景）散步或办事时，打开它，把走过的地方变成自己的游戏世界，并就地完成任务。
- **闭环关**：进入（打开停在上次的房间）→ 过程（拍照建房 / 探索移动 / 接任务 / 对话 / 战斗）→ 结果（经验、道具、任务结算、世界图扩大）→ 关掉重开原样继续。可反复用，世界随玩家真实活动持续生长。
- **厚度关**：五样里占四样——真实数据（照片判定、GPS 位置与朝向）、成套内容（任务模板集、NPC 人设集、道具与敌人图鉴）、多步流程（建房、任务链、战斗均为多步）、跨会话记忆（本地存档 + NPC 记忆）。集合总控不适用（本体就是一个完整世界，不是合集）。
- **默认能力冲突**：本体不是慧眼辨识。慧眼是问一次答一次、无状态；本游戏的看图判定只是闭环内的一步——判定结果要落进持久世界（房间、NPC、任务进度），且判定不确定时有确认与重拍流程。与默认能力同本体的功能不做：不做通用视觉问答、不做翻译、不做导航产品（GPS 只服务于玩家自建锚点之间的游戏任务，给 cardinal 方位与距离，不做逐路口导航）。
- **环境常识**：游玩场景都是日常戴眼镜的公共场所；拍照与手势动作都要求玩家先站定再操作（见第 11 节安全红线）。

## 2. 平台铁律在本架构的落点

| 铁律 | 架构落点 |
|---|---|
| 看图只有拍照→data URL→LLM 图片输入一条路，定格判定 | 全部「看」与「摆」判定走第 5 节统一判定管线；管线之外没有任何看图入口。条码类目标可用原生 BarcodeDetector，但第 1 阶段不用 |
| 没有手部追踪、没有连续视频理解、没有眼动 | 手势一律静态摆拍一张判定；「看向」= 头部朝向（AbsoluteOrientationSensor 四元数推导）+ 头稳事件 + 点头确认，不出现任何眼动表述 |
| LLM 看图会认错 | 判定结果强制结构化（认出什么 + 把握度 0–1 + 不确定项），过第 5 节把握度门控才落盘；认不准就明说并给重拍 / 玩家确认两条路，不许静默按准的走 |
| Agent 之间不能互调、不能后台常驻 | 整个游戏是一个 Agent、一个工程；多人靠自建后端且异步优先，眼镜端只在打开期间轮询 / 同步，没有任何后台行为 |
| API 清单纪律 | 第 3 节每个适配器都注明官方出处；查无名单（FileReader、sessionStorage 等 SOP 清单）一律禁用；版本敏感 API 做存在性守卫 |
| 裸错误码 | 第 12 节失败点全部映射现有码表 v1.14.0 的已有码；本架构不自拟新码，缺口按治理走 E9001 兜底 + 向登记处申请 |
| 绿色色阶禁纯白、手势优先按钮最少 | UI 层只用绿色色阶（最亮 #7dff9e）；主流程靠镜腿手势（单击确认 / 双击返回 / 滑动切换）+ 头部动作 + 语音跑完，每页手势映射写进 README |
| 480×352 运行时画布、单色绿 | 房间描述正文分页短行呈现；一屏只放一个决策点 |

## 3. 眼镜端分层

六层，依赖只能自上而下。游戏核心层不碰任何平台 API——所有平台能力都经适配器层注入，这样判定与规则可以在模拟器里用假数据跑通，真机只验适配器本身。

```
┌─────────────────────────────────────────────┐
│ 1 表现层 Pages（.ink）                        │
│   房间 / 拍照建房 / 地图 / 任务 / 对话 / 战斗   │
│   / 背包角色 / 门 / 存档系统 —— 共 10 页（§10）│
├─────────────────────────────────────────────┤
│ 2 交互层 Interaction                          │
│   键事件（Enter/Backspace/ArrowUp/Down）      │
│   头部：朝向推导、头稳、点头（onHeadGesture）   │
│   语音：ASR 输入、TTS 播报、预置台词兜底        │
├─────────────────────────────────────────────┤
│ 3 游戏核心 Game Core（纯逻辑，零平台 API）      │
│   世界图、移动、任务状态机、战斗结算、成长       │
│   NPC 对话编排、判定结果消费（只认结构化结果）   │
├─────────────────────────────────────────────┤
│ 4 判定层 Judge                                │
│   提示词模板、结构化输出解析与校验、把握度门控   │
│   安全标记（人脸 / 私人场所 / 危险物）           │
├─────────────────────────────────────────────┤
│ 5 适配器 Adapters（每项注明官方出处）           │
│   Camera / ImageLLM / Geo / Heading / Speech  │
│   / Store / NetStub（空实现）                  │
├─────────────────────────────────────────────┤
│ 6 基础设施 Infra                              │
│   err.js（裸码单点定义 + fail 出口）            │
│   存档双槽写协议、日志队列（可选件，未配静默）   │
└─────────────────────────────────────────────┘
```

适配器清单（API 均出自能力档案对应节，开发时逐个再对 aiui-dev references 原文复核）：

| 适配器 | 用途 | 官方 API | 权限 | 失败映射 |
|---|---|---|---|---|
| Camera | 拍照（建房 default、看任务 telephoto、广角场景 wide） | `ImageCapture.takePhoto({mode})`；Blob→data URL 走 `blob.arrayBuffer()` + 分块 `btoa` | CAMERA | E1001/E1002/E1009/E1010、E2005/E2013 |
| ImageLLM | 看图判定、房间生成、NPC 对话与战斗叙事 | `LanguageModel.availability/create`，user 消息 content 数组 `{type:'image_url', image_url:{url: dataURL}}`；`promptStreaming` 轮询 `read()` | 无（宿主托管） | E6001/E6002/E6003/E6005/E6011 |
| Geo | 当前位置、到锚点距离与 cardinal 方位换算 | `navigator.geolocation.getCurrentPosition/watchPosition`；错误码 1→E7003、2/3→E7002 | GEOLOCATION | E7002/E7003 |
| Heading | 拍照瞬间朝向、转头选出口、点头确认 | `AbsoluteOrientationSensor`（四元数→yaw）；`enableWorldAwareness` 后 `onOrientationStabilityChange`、`onHeadGesture('nod')` | 无 | E7001/E7006/E7008/E7010 |
| Speech | ASR 对话输入、TTS 播报 | `SpeechRecognition`（宿主麦克风，不选模式）；`speechSynthesis.speak`（11 音色，lang 不生效） | RECORD_AUDIO（ASR 无独立权限） | E3001–E3003/E3005/E3008 |
| Store | 本地存档分块读写、双槽轮换 | `localStorage` / wx 存储（二选一，第 1 阶段探针定，见 §7） | 无 | E5001–E5005 |
| NetStub | 联机同步接口的空实现 | 不发任何请求（第 3 阶段才接 `fetch` HTTPS） | 无 | 无——未配置时完全静默，不报错 |

设计原则两条，写死在核心层：

1. **规则归代码，叙事归 LLM。** 战斗伤害、任务成败、物品掉落、经验数值全部由核心层按确定规则结算；LLM 只负责把场景写成文字、把 NPC 台词说出来、把结算结果叙述一遍。LLM 输出的任何数值都不直接生效。
2. **判定不落盘，世界才落盘。** 照片原图与 data URL 用完即弃，永不进存档；进存档的只有判定产出的文字与结构化结果（§4、§7）。

## 4. 世界数据结构

全部结构是带版本号的 JSON。ID 用 `crypto.randomUUID()`（官方 web 参考有此 API）生成，房间 ID 另带玩家内序号便于人读（如 `r12`）。

### 4.1 房间 Room

```json
{
  "roomId": "r12",
  "name": "梧桐树下的长椅",
  "desc": "一条长椅靠在梧桐树下，落叶堆在椅脚。石板路往东去，草坪在西边。",
  "sceneType": "outdoor_park",
  "createdAt": "2026-10-29T10:00:00+09:00",
  "anchor": { "lat": 35.6812, "lng": 139.7671, "accuracyM": 18 },
  "exits": { "E": "r13", "W": "r9" },
  "pendingExits": ["N"],
  "entities": ["n31", "i07"],
  "visits": 3,
  "lastVisitAt": "...",
  "judge": { "confidence": 0.86, "recognized": ["长椅", "梧桐树", "石板路"], "uncertain": [] }
}
```

- `anchor` 可空：室内或定位失败时建的房没有锚点，只能靠出口图到达，不能接「走」类任务。定位失败不挡建房（降级，TTS 明说这间房没有定位）。
- `desc` 是 LLM 生成后经玩家确认的定稿文本；重访时不重新生成，保证世界稳定。玩家可改名（改名只改 `name`）。
- `judge` 只存判定摘要（认出什么、把握度），不存照片。

### 4.2 出口与方向

- 拍照瞬间读 Heading 的 yaw，换算到 8 方位（N/NE/E/SE/S/SW/W），取正向最近的 4 正向（N/E/S/W）之一作为「来路的反方向」基准——出口只用 4 正向，斜向只用于 GPS 任务的 cardinal 指引显示，与指向性 skill 的分工一致：眼前指引用相对方向、锚定任务用 cardinal + 距离。
- 从房间 A 面向 D 拍照建出房间 B 时：`A.exits[D] = B`，`B.exits[opp(D)] = A`，双向一次写定。
- 冲突处理：若 `A.exits[D]` 已有房间，不覆盖——新房改挂 `pendingExits` 并在地图页提示玩家选「替换 / 并存为岔路 / 放弃新房」。第 1 阶段实现「替换 / 放弃」两项，并存岔路放第 2 阶段。
- 朝向读不到（传感器无数据、室内磁扰导致 yaw 漂移过大）时：建房照常，出口方向由玩家用转头选向 + 点头手动指定，存档里该出口标记 `dirSource: "manual"`，不装作是传感器定的。

### 4.3 NPC、道具、敌人

```json
{
  "npcId": "n31", "roomId": "r12",
  "name": "守椅老人", "persona": "慢声细语，爱讲这棵树的往事",
  "origin": "由长椅与落叶生成，非真人",
  "memory": { "summary": "玩家答应帮他找丢失的纽扣。", "facts": ["玩家来过3次", "纽扣任务进行中"], "metCount": 3 },
  "questIds": ["q08"]
}
```

- NPC 只能由场景里的**物**生成（长椅→守椅人、邮筒→邮差、自动贩卖机→夜班店员），人设是物的拟人化；照片里有真人时不以真人为原型（§11）。
- `memory.facts` 上限 12 条，超了由 LLM 把旧 facts 压进 `summary` 再清空（压缩只在对话结束时做，结果玩家可见可删）。
- 道具 Item：`{itemId, name, kind: quest|consumable|equip|material, desc, count}`，来源只能是房间实体或任务奖励，不凭空刷。
- 敌人 Enemy 由房间实体敌化生成（如「落叶堆里的甲虫」），数值由核心层按玩家等级与房间序号派生，LLM 只给名字与描写。

### 4.4 任务 Quest

```json
{
  "questId": "q08", "kind": "look|walk|gesture|head|talk",
  "title": "找回纽扣", "giverNpcId": "n31",
  "state": "offered|active|verifying|done|failed",
  "targetRoomId": "r12", "targetRef": "长椅下",
  "steps": [ { "do": "回到长椅所在的房间", "via": "walk" }, { "do": "拍一张长椅近景", "via": "look" } ],
  "reward": { "xp": 20, "itemId": null }
}
```

- 任务目标只能引用**玩家自己已建的房间与其中的实体**（`targetRoomId` 必须已存在于世界索引）。系统永不生成「去某个你没去过的地方」类目标——新地方只能由玩家自己走过去拍，拍完才可能成为后续任务目标。
- 五种 `kind` 对应五种玩法（§6），第 1 阶段每种一个样板任务，挂成一条 5 步主线链，链的每一步解锁下一步。

### 4.5 玩家 Player

```json
{
  "playerId": "（本地生成 UUID，上云预留）",
  "name": "（玩家自取，可改）",
  "level": 1, "xp": 0, "hp": 20, "hpMax": 20,
  "titles": [], "currentRoomId": "r1",
  "bag": ["i01"], "stats": { "rooms": 1, "walks": 0, "battlesWon": 0 }
}
```

成长只认四种来源：建房 XP、任务 XP、战斗 XP、到访新锚点 XP。等级阈值与数值表放核心层常量，第 1 阶段用小表（1–5 级）验证循环，第 2 阶段扩表。

## 5. 判定流程（统一管线）

所有看图判定（建房、看任务验证、手势开门）走同一条管线，不许各页面各写一套：

```
玩家站定 → 单击拍照（交互门内触发）
  → Camera.takePhoto(mode) 得 Blob
  → blobToDataUrl（arrayBuffer + 分块 btoa，禁 FileReader）
  → 拍时快照：Heading yaw + Geo 位置（能取则取，取不到不挡）
  → ImageLLM.promptStreaming(结构化提示词 + data URL)
  → 解析返回 JSON → schema 校验（字段/类型/枚举）
  → 把握度门控（下表）
  → 玩家确认 / 改名 / 重拍
  → 核心层结算 → Store 落盘（只落文字与结构化结果）
  → TTS 播报结果一句 + 屏显摘要
```

结构化判定结果（判定层唯一出口，核心层只认这个形状）：

```json
{
  "ok": true,
  "recognized": ["长椅", "梧桐树"],
  "sceneSummary": "公园一角，有长椅和大树",
  "confidence": 0.86,
  "uncertain": ["远处的人影看不清，未计入"],
  "facesPresent": false,
  "privateOrDanger": false,
  "gesture": null
}
```

把握度门控（初始值，第 1 阶段真机数据回来后校准，校准记录写进本文件变更日志）：

| confidence | 处置 |
|---|---|
| ≥ 0.75 | 生成结果呈现给玩家，点头 / 单击即确认落盘 |
| 0.45 – 0.75 | 明说「没太看准」，列出 `uncertain`，玩家三选：确认 / 改一处再确认 / 重拍 |
| < 0.45 | 不落盘，明说没看清，只给重拍或放弃；连续 2 次低把握，提示换角度 / 换光线 |

其他判定规则：

- 解析失败、字段缺失、枚举外的值：一律按判定失败处理（E6011 / E6009），走重拍或手动录入（玩家口述房间名与一句描述，ASR 转文字落盘，`judge.confidence` 记 0 并标 `manual`），不许拿半截 JSON 硬凑世界。
- `facesPresent = true` 时：NPC 生成环节跳过照片中的人物，只用物生成；判定摘要里只记「画面里有人，未用作 NPC」，不描述其长相。
- `privateOrDanger = true` 时（判定为私人室内、禁入区域、危险场所）：拒绝建房，明说原因，给玩家「这是我自己的公开活动空间」申诉确认一次的机会，确认后才建且该房标记永不进入共享（第 3 阶段审核位同样拦）。
- 手势判定是同一管线的特例：`gesture` 字段返回认出的手势名与把握度，门控阈值相同；低于阈值不算失败惩罚，只算「门没认出来」，可重拍，不扣任何数值。

## 6. 五种玩法（眼镜特色准入）

收录标准：手机和平板做不了、或做出来是假的（无第一人称视角、无头部朝向、无随身 GPS 实景），才有资格进玩法表。每种玩法第 1 阶段各配一个样板任务，五样板串成主线链（§10）。

| 玩法 | 输入与 API | 判定 / 结算 | 第 1 阶段样板 |
|---|---|---|---|
| 看 | 走到目标前，telephoto / default 拍照 | 第 5 节管线验证目标在场且是目标物 | 在自建房间里拍到任务指定物（如长椅下的纽扣盒——以房间实体为准） |
| 走 | GPS 实时位置 vs 目标房锚点；屏显 cardinal 方位 + 距离（米），到达半径默认 30 米（D4） | 距离 ≤ 半径且 accuracy 不劣于半径 → 到达；accuracy 太差时明说定位不准、请到开阔处 | 从房间 A 走到已建的房间 B（两房都要有锚点） |
| 摆 | 静态手势摆好，拍照 | 管线手势判定（§5 特例）；开门是标志玩法，源自描红系列一步一验 | 手势开门：被锁的门要求一个静态手势（D3 推荐张开手掌），摆对开门、进隐藏房或得道具 |
| 动 | AbsoluteOrientationSensor 推导 yaw/pitch；头稳 + 点头 | 转头选出口：yaw 落入出口方向扇区并头稳 0.8 秒高亮，点头确认移动；点头也作全局确认 | 在房间里转头选东出口并点头通过 |
| 说 | ASR 对 NPC 说话；LLM 以人设 + 记忆作答；TTS 播报 | 对话内容不做对错判定；任务型对话由核心层查关键词 / 任务状态（如交还物品靠背包状态，不靠 LLM 说法） | 向 NPC 交还任务物品并听它说出记忆里的一件事 |

语音兜底：ASR 不可用、环境太吵或识别连续失败时，对话页给出 3 条预置台词供滑动 + 单击选择——「说」玩法的闭环不因 ASR 挂掉而断。TTS 播报每条限长（房间描述分段播报、可双击打断回上层；TTS 无 cancel API，打断靠页面切换与队列纪律实现，文案不承诺「随时停」之外的能力）。

战斗（文字回合制，长在「看 / 动 / 说」之上，不单列第六种）：在房间遭遇敌人 → 回合循环（攻击 / 防御 / 技能 / 道具 / 逃跑，滑动选 + 单击定，或语音口令）→ 核心层按数值结算 → LLM 只把每回合写成一句话播报。敌人不追人、不实时，全部回合制，与「不能后台常驻」相容。

## 7. 存档 schema（单机阶段）

载体：智能体隔离存储。`localStorage` 与 wx 存储二选一，由第 1 阶段开工首日的存储探针定（探针验四件事：单键值大小上限、总配额量级、写后杀进程重进可读、JSON 大对象往返无损）；`navigator.storage` 官方只有入口一句话、无方法细节，**不用**，等官方给细则再议。

分块键设计（前缀 `mud1.`，1 是存档结构大版本）：

| 键 | 内容 |
|---|---|
| `mud1.active` | 当前活槽标记：`"A"` 或 `"B"` + 该槽 manifest 的 updatedAt |
| `mud1.A.manifest` / `mud1.B.manifest` | 槽清单：`{ saveVersion, playerId, updatedAt, blocks: {player: n, rooms: n, social: n}, checksum }` |
| `mud1.<槽>.player` | 玩家块（§4.5 全量） |
| `mud1.<槽>.world.index` | 房间索引：`[{roomId, name, exits 摘要, hasAnchor}]`，进游戏只读索引不读全部房间 |
| `mud1.<槽>.room.<roomId>` | 一间房一块（§4.1 + 该房实体全量） |
| `mud1.<槽>.social` | NPC 块 + 任务块（NPC 人数与任务数在单机阶段量级小，合一块；第 2 阶段量大再拆） |
| `lastError` | 错误码规范的既有键（err.js 写），不属存档双槽，坏档不影响它 |

写协议（双槽轮换，防写一半断电 / 被杀）：

1. 永远往**非活槽**写：依次写 player、world.index、各 room 块、social；
2. 最后写该槽 manifest（`checksum` = 各块字符串长度与简易哈希的组合，只作完整性自检，不作安全用途）；
3. 全部写完才改 `mud1.active` 指向新槽。写一半失败，活槽仍是上一份完整档，失败按 E5001 / E5003 报码，玩家无感继续用旧档（屏显只提示「刚才的进度没存上」一句 + 码）。

读协议：读活槽 manifest → 校验 saveVersion 与 checksum → 任一块解析失败则整槽弃用、回退另一槽并明说「存档退回了上一次保存」（E5002）；两槽都坏才开新档，且坏档原文保留在 `mud1.corrupt.<时间戳>` 键里供排查，不静默丢。`saveVersion` 不兼容时先跑迁移函数链，无迁移路径则按 E5004 处理（保留旧档键、开新档、明说）。

容量纪律：照片永不入档；单房 desc 限 200 字、NPC facts 限 12 条（§4.3）；房间数软上限 200 间（第 1 阶段远达不到，写死常量防失控），到上限时提示归档最旧的无任务房间（第 2 阶段做，第 1 阶段只提示不删）。

预留字段（第 1 天就写进 schema，第 3 阶段才启用）：每块带 `playerId`、`updatedAt`（ISO +09:00）、`rev`（本地递增修订号，作上云冲突判断的客户端依据）。导出：本地导出无官方文件 / 剪贴板 API 可用，第 1、2 阶段**不做导出功能**，只保证数据结构可导出；真正的导出与上云同步一起在第 3 阶段经后端实现。README 与 UI 不许提前宣传导出可用。

## 8. 网络层空实现（第 1、2 阶段）

NetStub 接口形状先定死，实现为空转：

```js
// net.js — 未配置后端时：isEnabled() 恒 false，所有方法立即返回
// { status: "disabled" }，不发请求、不报码、不写 lastError、不提示玩家。
export const net = {
  isEnabled(),        // 读配置常量 BACKEND（工程内默认 null）
  async syncUp(blocks), async syncDown(),
  async fetchNearby(anchor), async postTurn(sessionId, turn)
};
```

核心层只依赖接口形状，调用点对 `disabled` 的处理就是「照常单机玩」。配置了后端但请求失败时（第 3 阶段起）才按 E6004 / E6007 / E6008 报码，且同步失败永不挡单机玩法——这是码表总原则「可选件失败完全静默」的同一口径。

## 9. 后端接口形状（第 3、4 阶段，只设计不实现）

部署形态设想：复用 rokidpost 已验证的 Cloudflare Workers + D1 模式（前门 + 结构化回单），独立仓库、独立域名。本节只定接口形状与数据纪律，建站是第 3 阶段开工时另行立项的事。

身份：普通 Agent 拿不到 Rokid 账号信息，`navigator.id` 是与智能体 + 设备绑定的不透明 ID、官方明示不得当凭据。故后端自建身份：首次同步时眼镜端生成 `playerId` + 本地密钥（HMAC，`crypto.subtle` 仅支持 SHA / HMAC——签名校验按此设计，不设计加密传输，传输靠 HTTPS），后端注册后发回会话令牌。换设备找回靠第 3 阶段设计的恢复码（玩家自己保管），不承诺「登录账号即找回」。

接口（全部 HTTPS、JSON、带 `playerId` 与签名头；版本前缀 `/v1/`）：

| 接口 | 用途 | 关键纪律 |
|---|---|---|
| `POST /v1/players/register` | 注册 playerId、发令牌 | 幂等：同 playerId 重复注册返回原记录 |
| `GET /v1/saves/manifest` | 拉云端各块 rev 与 updatedAt | 只下清单，块按需拉，避免整档流量 |
| `PUT /v1/saves/blocks/<blockKey>` | 按块上行（player / room.<id> / social） | 带客户端 `rev` 与 `baseRev`；冲突返回 409 + 云端块，前端走「后写者提示、先合并索引」策略，永不静默覆盖房间块 |
| `GET /v1/saves/blocks/<blockKey>` | 按块下行 | 与本地双槽协议衔接：下行先落非活槽，校验后翻槽 |
| `POST /v1/rooms/share` | 提交一间房为共享房 | 进审核队列，状态 `pending`；未过审对任何其他玩家不可见（§11 审核位） |
| `GET /v1/rooms/nearby?gx=&gy=` | 拉附近已过审共享房 | 坐标只收**粗化网格**（约 100 米格），服务端不收精确经纬度；返回房也不带精确锚点 |
| `POST /v1/sessions` / `POST /v1/sessions/<id>/turns` / `GET /v1/sessions/<id>` | 多人会话：第 4 阶段异步任务协作 + 同地回合制 | 回合制以服务端序号定序；眼镜端只在打开期间轮询，无推送、无后台 |
| `POST /v1/reports` | 玩家举报共享房 / NPC 文案 | 举报直达审核队列，处理结果回执进玩家收件箱（下次打开时拉） |

后端存的东西与不存的东西：存玩家块、房间块（文字与结构化结果）、共享与审核状态、会话回合；**永不上传照片原图与 data URL，永不上传精确 GPS 轨迹**——锚点上行前在眼镜端粗化到网格，本地档的精确锚点不出眼镜。

## 11. 安全红线（从架构阶段写死，全阶段适用）

1. **任务目标白名单**：任务只能指向玩家自己拍过、已建档的房间与实体（§4.4 在数据结构上强制——`targetRoomId` 必须已存在）。系统不生成指向陌生地点、私人住所、禁入区域的目标，不用奖励诱导玩家去没去过的地方。
2. **建房安全判定**：判定结果带 `privateOrDanger` 标记（§5），疑似私人 / 危险 / 禁入场所默认拒建，申诉确认后建的房永久排除共享。
3. **不拍他人正脸生成 NPC**：NPC 只由物拟人化生成（§4.3）；判定检出人脸只记「有人在场」，不描述、不命名、不生成对应 NPC。玩家自己摆拍的手势照只判手势、判完即弃。
4. **行动安全**：拍照、摆手势、转头选向之前，页面先给一句「站定再操作」；「走」任务只显示方位与距离，不催促、不倒计时、不用「快到了」类话术逼玩家边走边看；到达判定宁可迟到不可误报（accuracy 参与判定，§6）。
5. **位置隐私**：精确锚点只存眼镜本地；上云与共享一律粗化网格（§9）；README 与 UI 明说这一条。
6. **联机内容审核位**：共享房与玩家起名（房间名、角色名、NPC 改名）进共享前必过审核队列——自动过滤先行、人工复核可下架，未过审不可见（第 3 阶段实现，第 1、2 阶段在数据结构上预留 `shareState` 字段默认 `private`）。LLM 生成文案在共享时同样过审。
7. **未成年与消费**：本游戏无内购、无付费点（AIUI 也无支付通道，不设计）；文案不做成瘾性催促（不搞限时消失奖励、不搞连续登录惩罚）。
