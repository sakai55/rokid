# Rokid デフォルト能力衝突監査 (Built-in Capability Conflict Audit)

[中文](SKILL.md) | [English](SKILL.en.md) | 日本語
中文版（2026-10-29 時点）を正本とする。本書と正本で解釈が分かれる場合は、正本を優先する。

**Version: 1.0.1** — バージョンの付け方のルールは文末に置いた。初出は、2026-10-25 に GO の指示で実施した、全 Agent 122本を対象とする初の監査である。完全な報告書は、保守担当者のワークスペース `~/workspace/rokid/audit-builtin-conflicts/REPORT.md` にある。

## この skill が必要な理由

グラス本体には、ひととおりの機能が最初から入っている。その標準機能を名前だけ変えて Agent として作り直しても、新しい価値にはならない。利用者は標準機能を開けば足り、わざわざ用意した Agent は要らなくなる。審査の場でも説明が立たない（SOP の Governing rule が置く厚みゲートでは、デフォルト能力と同じ本体のものは、その時点で対象外となる）。

本書の役割は、「何を衝突とみなすか」の物差しを固定しておくことにある。新しい Agent の企画時に自分で照らせること、Agent 群全体を同じ物差しで見直せること、ルート README の衝突バッジの出どころを1か所に定めること。この3点のために置く。

## デフォルト能力ベースライン（判定の前に、最新版であることを確かめる）

ベースラインは、印象や思い込みで決めない。公式資料と公開された情報だけを根拠とする。現行のベースラインは次のとおりである（2026-10-25 に確定。根拠：公式の能力登録表 `docs/CAPABILITIES.ja.md` の項目 C1017、C8013、公式のグローバル向け製品ページ、公開レビューでの実証）。

1. **リアルタイム翻訳**（89言語）：会話の翻訳字幕に加え、撮影した文字、メニュー、標識の翻訳にも対応する。AI クイックコマンドには「写真を撮って中国語に翻訳する」があらかじめ用意されている。
2. **リアルタイム字幕（Intelligent Captioning）**：同言語の会話をその場で画面に表示する。字幕は履歴に残り、あとから読み返せる。
3. **会議の文字起こし + AI 要約**：話者を識別しながら文字起こしし、要約を自動で作る。音声メモも標準機能に含まれる。
4. **テレプロンプター**：原稿を画面に表示し、読み上げる速さや間に合わせて自動でスクロールして追従させる。
5. **慧眼識別 / AI 視覚 Q&A**：「Hi Rokid」アシスタントとカメラを使い、目の前の物を見て識別し、文字や標識を読み、場面に関する質問に答える。
6. **視覚化 AR ナビゲーション**：進む方向の矢印に加え、速度、所要時間、到着時刻を画面に表示する。
7. **パーソナルアシスタント AI Q&A、通知表示、写真・録画、通話／音楽**。

再監査の際は、まずベースライン自体が変わっていないかを確かめる。新しい機種、新しいシステムの版、公式に追加された機能は、いずれもベースラインを広げうる。変わっていた場合は、文末のルールに従ってバージョンを上げ、影響を受ける区分を並べ直す。

## 判定の区分（3区分、重ねない）

判定の対象は、Agent の**本体の仕組み**である。利用者に代わって「何をするか」、その事柄そのものを見る。どの経路を借りているかは対象にしない。

- **第1区分 · 直接衝突**：本体そのものが何らかのデフォルト機能であり、付け加えたのが小さなひねり1層にとどまるもの（出し方を変える、小さな絞り込みを足す、ある時間の範囲だけを切り取る、といったもの）。GO が名指しした見本が `chat-catchup`（SO01）である。内蔵の字幕はもともと履歴に残り読み返せるのであって、「頭を振って直近15秒の要約を出す」は小さなひねりにすぎず、余分なものであるという判定になる。扱いは次のとおりとする。再構成して審査に出してはならない（SOP の絶対条件）。取り下げるか、草稿を削除するかは GO の裁定を待ち、自動では実行しない。
- **第2区分 · 高度な重なり**：本体の大半が、デフォルト機能を「ひと言聞く／ひとつ開く」だけで済んでしまい、残るのが薄い閉ループ1層だけのもの（文字を読んだあとに登録や照合を1手順足す、Q&A のあとに段階的な案内を1手順足す、など）。残すかどうかは GO がクラスターごとに裁定する。裁定が出るまでは審査に出さない。
- **第3区分 · テスト待ち**：第1区分にも第2区分にも入らない、番号付きの Agent はすべて一律にここへ入れる。この区分が意味するのは「デフォルト能力との関係は、実機テストのあとに定める」ということであり、「衝突しないことが確認済み」という意味ではない。新しい Agent はまずここへ入れ、監査を経てから区分を変える。

衝突とみなさない場合（第3区分に入れ、報告書に理由を明記する）：デフォルト能力が閉ループの中の1手順にすぎず、登録 → 待ち受け／範囲を区切ったカバー／順を追ったカウント／あとからの再生という閉ループそのものが内蔵機能には無い場合である。例として、`drop-search` の範囲を区切ったカバー探索、`my-bus-watch` の対象路線に絞った待ち受けフィルターが挙げられる。

## 監査の進め方

1. **対象を洗い出す**：リポジトリの分類ディレクトリ配下にある Agent をすべて列挙する（ルート README の一覧を基準に、差分が無いか照らす。引退済みで残してあるものは一覧に入れず、区分けにも参加させない）。
2. **本体を読む**：PLAN の登録行と README の仕組みの説明を1本ずつ読み、本体をひと言で書き出す。仕組みの実装まで読み取れないものは、`pages/index/index.ink` と AGENTS.md を読んで確かめ、slug から推測で決めない。
3. **ベースラインと照らす**：本体を7項目のベースラインと1つずつ照らし、上の節の区分に従って振り分ける。際どいものは「デフォルト機能でどこまで済むか、Agent が加えている層は何か」を明記したうえで、第2区分か第3区分かを決める。
4. **報告書を出す**：ワークスペースの報告書を更新する（項目ごとの対照表とする。第1区分は全件を列挙し、第2区分はクラスターごとに列挙し、第3区分はまとめて示す）。ベースラインの版と、今回使った本書の版を明記する。
5. **バッジを同期する**：ルート README の一覧にある衝突バッジは、報告書の区分を基準とする（第1区分＝直接衝突、第2区分＝高度な重なり、第3区分＝テスト待ち）。バッジの定義は凍結されており、同期を口実に定義を新たに加えたり変えたりしてはならない（GO が 2026-10-25 に裁定）。
6. **裁定の余地を残す**：第1区分の処置と、第2区分のクラスターごとの残否は、GO の裁定事項として報告するだけにとどめる。裁定が出る前に削除しない、審査に出さない、裁定待ちのものを処置済みと書かない。

## バージョンの付け方

本書はバージョン番号付きで改訂していく。改訂の際は、次の3点を必ず同時に行う。バージョン番号を上げること、下の変更履歴に1件追加すること、報告書に根拠とした本書のバージョンを明記すること。

- **PATCH（x.y.Z）**：言い回し、例、手順の細部の修正。判定の区分とベースラインは変わらない。
- **MINOR（x.Y.0）**：ベースラインへの項目の追加・削除、判定への新しい場合の補足、手順への段階の追加。区分が変わる可能性があるため、影響を受ける Agent を変更履歴に明記しなければならない。
- **MAJOR（X.0.0）**：区分の体系や物差しそのものの根本的な変更（GO が判定基準を置き換える場合など）。全 Agent を新しい物差しで並べ直し、バッジをすべて同期しなければならない。
