# Rokid Boutique Batch Acceptance
[中文](SKILL.md) | English | [日本語](SKILL.ja.md)
Translated from the Chinese version (as of 2026-10-29). In case of conflict, the Chinese version prevails.

The acceptance layer for the boutique line. Production (three gates, 9-step SOP, pack/preview/README/GitHub sync) lives in `rokid-agent-sop` — this skill covers only how a finished batch gets *verified*. A batch is accepted from its **built files**, never from its ledger, its PLAN notes, or its own report: a claim counts only when the built project shows the same fact.

Run it after building, **before** packing counts as done, before pushing, and before registering the batch (root README list, PLAN tables, goal timelines). The boutique daily cron (`rokid-boutique-daily-10`) carries a condensed copy of these checks in its body; when the two disagree, this skill is the authority.

## Check the structure in the built files

- Count each agent's pages from the built project files (`app.json` page list + `pages/` tree), and record the count next to the agent's name.
- Fail any non-game agent with only one page: a single page cannot carry entry → process → result. (Games follow the SOP loop-gate relaxation, but a boutique game still needs its thickness — levels/progress/content set must be present in the files.)
- Compare page lists and built file sizes across the whole batch. Agents that share one skeleton with only the labels changed are **isomorphic — fail**. Ten near-identical `.ink` file sizes are evidence, not coincidence.
- Treat every ledger claim and design note as unproven until the built files show the same fact.
- **Heavy agents — count distinct pages.** A heavy-designated agent (the daily batch carries 2) must show **20 or more distinct pages** in the built files: reconcile the `app.json` page list against the `pages/` tree, one entry each, and every page must differ functionally in content and wiring. States of a single page, demo steps, and screenshot variants never count as pages. Spot-check 5 pages for genuine difference; merge look-alike pages in the count and re-check the total. Under 20 after merging — fail; do not count it.

## Verify every claimed gate in code

- **Content set — count it.** For each claimed set, count the items in the built files and record the number (stations, songs, questions, stalls, steps…). A set that cannot be counted does not exist.
- **Loop — find the call.** For each claimed loop step, locate the API call that step needs in the built files (head orientation / `onHeadGesture`, ASR, TTS, camera…). A step with no call behind it is unwired, and the claim fails. Permissions in `app.json`/`package.json` must match the features actually wired — never accept a zero-permission claim for a camera/sensor feature.
- **Cross-session memory — find the persistence code.** Where cross-session memory is claimed, find the storage/write code (and record the key name). No persistence code, no claim.
- **Error-code wiring — grep it.** For any agent claiming error-code integration (mandatory for new boutique agents), search the built files for the wiring: every user-visible failure path must surface a global code in bare form (`E####`, per the repo-root `ERROR-CODES.md`), persist `lastError` (full code + slug + version + original text), and the README must carry an "Error Codes" section listing the codes used. A failure path that shows raw error text with no code — fail. Also grep the built files for `FileReader`: any hit is an automatic fail (the API does not exist in the Ink runtime — proven on device by field report E2005).
- **API-list compliance — grep the battery, trace the calls.** For every agent, grep the built files for the absent-list battery and stale patterns defined in the SOP's API discipline lesson (`FileReader`, `sessionStorage`, `XMLHttpRequest`, `URL.createObjectURL`, `DOMParser`, `structuredClone`, `queueMicrotask`, `Notification`, clipboard APIs, the observer pair, `ServiceWorker`, `new Worker(`, `canvas.toDataURL`, `captureStream`, `getDisplayMedia`, `applyConstraints`, `TextDetector`, `onclick=`, `Page(`, `App(`, `Widget(`, `require(`, the legacy `workers` field — the full list is in `rokid-agent-sop/SKILL.md` rule 2 and its `API-AUDIT.md`). Any hit is an **automatic fail**: those APIs are verified absent from the official reference, so their presence means browser-habit code that will only fail on a real device. Then spot-trace every non-trivial API call in the built files back to its official reference entry (aiui-dev `references/apis/` or upstream `documentation/3-api/`); a call that cannot be traced fails that agent's wiring claim. Version-sensitive APIs (arrived in Ink 0.15–0.19; table in `API-AUDIT.md`) must carry an existence guard (`typeof` / `wx.canIUse()`).
- **Glasses-only capability — find the call, run the phone test.** (GO, 2026-11-01: the travel-hub batches read as record apps a phone does better.) For every agent, identify the glasses-only scenario capability claimed in the ledger/README — hands-busy first-person capture via nod/voice trigger, look-to-point or dwell confirmation, head-heading registration, GPS cardinal + distance anchored guidance, in-view step-by-step guidance with per-step photo verification (the tracing shell is the archetype) — and find its API wiring in the built files. Then run the substitution test: if a phone app could do the same scenario flatly, or better, the capability does not count however it is dressed. A checklist / records / calculator / phrasebook page set is not a capability; a photo button or a TTS readout bolted onto a record app is not scenario-ized use. The capability must be a loop step whose removal breaks the loop. For heavy hubs, the 5-page spot-check doubles as the sampling for this check: if the sampled pages are all record-type pages, the agent fails.
- **Review video — probe it.** (GO, 2026-11-02: from the next run, review materials must include a 15-second video.) Every boutique agent must carry one 15-second video, produced at build time rather than backfilled at the device stage: find the MP4 at the recorded path (`screenshots/<slug>/preview-<slug>-video.mp4`), probe it with ffprobe (duration 14.5–15.5 s, ≤50 MB), and extract frames to confirm it shows 1–2 core flows actually running — a scripted preview walkthrough — not a slideshow of still screenshots. The README's Review Submission Preview Media must list the video, with total media files in the official 3–5 range. The README's Preview Media entry must also link the video as a clickable direct-download (its raw.githubusercontent URL), not a bare path (GO, 2026-11-03). Flows the preview cannot present (GPS / camera / device-only states) are noted as such in the README; the video shows only what the preview can honestly show. Missing, out-of-range, slideshow-substituted, or listed without its download link — fail.
- **Agent icon — verify the file.** (GO, 2026-11-03: every agent submits with a custom DNA-strand icon; the design was approved in full the same day, including the single neutral grey strand for agents with no series.) Every boutique agent must carry its icon at `icons/<slug>.png`: verify the file exists, is a PNG at 1024×1024, and matches what the repo generator (`icons/generate_icons.py`) produces for that slug — one strand per series in the agent's badge composition, in badge order, weights 1.0 / 0.65 / 0.5 by position, bundle axis and texture picked by the slug seed from the generator's fixed sets; an agent with no series badge carries a single neutral grey strand. When in doubt, regenerate and compare hashes — generation is deterministic. Missing, wrong-sized, the Studio default icon, or a hand-made substitute — fail.
- **Placeholders stay labelled.** Any placeholder or sample feature is labelled as a placeholder in the interface and in the notes, and is never counted as wired.

## Count only what passes — and report the rest

- An agent counts toward the batch only when every claim it makes passes the checks above.
- Report each failed agent with the check it failed and the built-file evidence, and put the batch shortfall at the **top** of the report. Never backfill the count with a thin replacement, never lower a gate to reach the daily number, and never recount an agent that failed the same check after a cosmetic relabel.
- Remedies that keep the standard: merge thin agents that belong to one scenario into a single scenario agent (the originals stay archived, never deleted), or thicken a failed concept with a real content set / multi-step flow and rerun every check from the built files.

## Versioning of this skill

This skill iterates in place, semver:

- **patch** (1.0.x): wording fixes, added evidence examples, a new isomorphism tell.
- **minor** (1.x.0): a new check, a new counted-claim type, a new failure case.
- **major** (x.0.0): a gate-level change (what counts as passing changes meaning).

Every change: bump `version:` above, append a Change Log entry below (date, what production run taught it, what changed), update the installed mirror at `~/workspace/custom-skills/rokid_boutique_acceptance/SKILL.md` in the same turn, and push both in one commit. Lessons that apply to all production (not just acceptance) go to `rokid-agent-sop` instead — do not duplicate them here.
