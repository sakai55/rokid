# Rokid Boutique Batch Acceptance

[中文](SKILL.md) | [English](SKILL.en.md) | 日本語
中文版（2026-10-29 時点）を正本とする。本書と正本で解釈が分かれる場合は、正本を優先する。

本書は、ブティックラインの検収手順である。製作そのもの（3つのゲート、9ステップの SOP、梱包、プレビュー、README、GitHub への同期）は `rokid-agent-sop` が担い、本書が扱うのは「出来上がったバッチをどう判定するか」だけである。

判定の根拠は、常にビルド済みの成果物に置く。台帳、PLAN のメモ、検収する側の報告そのものは根拠にならない。「実装した」「用意した」という主張は、ビルド済みのプロジェクトの中に同じ事実を確認できて初めて認める。

実施の時期は、ビルドが終わってから、梱包を完了扱いにする前、プッシュする前、バッチを登録する前（ルート README の一覧、PLAN の表、目標のタイムラインへの反映前）とする。ブティックラインの日次 cron（`rokid-boutique-daily-10`）の本文には、この確認の要約版が組み込まれている。要約版と本書が食い違う場合は、本書を正とする。

## 成果物から構造を確認する

- Agent ごとに、ビルド済みプロジェクトの `app.json` のページ一覧と `pages/` ツリーからページ数を数え、Agent 名と並べて記録する。
- ゲーム以外でページが1枚だけの Agent は不合格とする。1枚では「入る → 進める → 結果が出る」という流れを成立させられないためである。（ゲームについては SOP のループゲートの緩和が適用される。ただしブティック枠のゲームでも厚みは別途必要であり、レベル、進行、コンテンツ集合がファイルの中に実在しなければならない。）
- バッチ全体でページ一覧とファイルサイズを見比べる。ラベルだけを差し替えて同じ骨格を使い回している Agent があれば、**同型として不合格**にする。ほぼ同じサイズの `.ink` が10本並ぶのは、偶然ではなく使い回しの証跡として扱う。
- 台帳の主張も設計メモも、成果物で裏が取れるまでは未確認として扱う。
- **重厚 Agent — ページは「別物であること」を数える。** 重厚と指定した Agent（日次バッチには2本含まれる）は、ビルド済みの成果物の中に**互いに異なるページを20以上**備えていなければならない。`app.json` のページ一覧と `pages/` ツリーを突き合わせ、1件を1ページとして数え、各ページが内容と配線の両面で別物であることを条件とする。同じページの状態違い、デモの手順、スクリーンショットのバリエーションはページに数えない。任意の5ページを抜き出して本当に別物か確かめ、似通ったページは1つにまとめてから合計を数え直す。まとめた結果が20に届かなければ不合格とし、実績に数えない。

## 主張は1件ずつコードで裏付ける

- **コンテンツ集合 — 実物を数える。** 主張した集合ごとに、ビルド済みファイルの中の項目を実際に数えて件数を記録する（駅、曲、設問、屋台、手順など）。数えられない集合は、無いものとして扱う。
- **ループ — 呼び出しまで追う。** 主張したループの段階ごとに、その段階に必要な API 呼び出しがビルド済みファイルの中にあるか探す（頭の向き／`onHeadGesture`、音声認識、音声合成、カメラなど）。呼び出しが見つからない段階は未配線であり、その主張は認めない。`app.json`／`package.json` の権限は、実際に配線した機能と一致していなければならない。カメラやセンサーを使う機能で権限ゼロを主張することは認めない。
- **セッションをまたぐ記憶 — 永続化のコードを探す。** セッションをまたぐ記憶を主張する場合は、保存処理のコードがあるか探し、キー名を記録する。永続化のコードが無ければ、その主張は認めない。
- **エラーコードの配線 — grep で確認する。** エラーコード連携を主張する Agent（ブティック枠の新規 Agent では必須）については、ビルド済みファイルを grep してエラーコードの配線を確認する。利用者の目に触れる失敗経路はすべて、リポジトリ直下の `ERROR-CODES.md` に従い、裸の形式（`E####`）のグローバルコードを表示し、`lastError`（コード全文 + slug + バージョン + 元の文面）を保存しなければならない。README には、使っているコードを列挙した「错误码」の節が必要である。コードを伴わず元のエラーメッセージだけを表示する失敗経路があれば不合格とする。あわせてビルド済みファイルを `FileReader` で grep し、1件でも当たれば自動的に不合格とする（この API は Ink ランタイムに存在せず、実機報告 E2005 で裏付けが取れている）。
- **API 一覧への準拠 — まとめて grep し、呼び出しの出どころをたどる。** すべての Agent について、SOP の API 規律の回で定めた不在リストの一括対象と旧来のパターンを、ビルド済みファイルに対して grep する（`FileReader`、`sessionStorage`、`XMLHttpRequest`、`URL.createObjectURL`、`DOMParser`、`structuredClone`、`queueMicrotask`、`Notification`、クリップボード API、Observer のペア、`ServiceWorker`、`new Worker(`、`canvas.toDataURL`、`captureStream`、`getDisplayMedia`、`applyConstraints`、`TextDetector`、`onclick=`、`Page(`、`App(`、`Widget(`、`require(`、旧式の `workers` フィールド — 一覧の全文は `rokid-agent-sop/SKILL.md` のルール2と、その根拠である `API-AUDIT.md` にある）。1件でも当たれば**自動的に不合格**とする。これらの API は公式リファレンスに載っていないことが確認済みであり、成果物の中に残っているということは、ブラウザ向けの書き方が紛れ込んでいて実機で初めて落ちるコードだということになる。続いて、ビルド済みファイルの中の自明でない API 呼び出しをすべて抜き出し、公式リファレンスの該当項目（aiui-dev の `references/apis/`、または上流の `documentation/3-api/`）までたどる。たどり着けない呼び出しがあれば、その Agent の配線に関する主張は認めない。バージョン依存の API（Ink 0.15–0.19 で追加されたもの。対応表は `API-AUDIT.md` にある）には、存在確認のガード（`typeof`／`wx.canIUse()`）が付いていなければならない。
- **プレースホルダは、プレースホルダと分かるようにしておく。** プレースホルダやサンプルの機能は、画面上でもメモの中でもその旨を明示し、配線済みの実績には決して数えない。

## 数えるのは合格分だけ、不合格は報告に残す

- バッチの実績に数えるのは、上記の確認を、みずから主張したすべての項目について通過した Agent だけとする。
- 不合格になった Agent は、落ちた確認項目とビルド済みファイルに基づく根拠を添えて報告し、バッチとしての不足分は報告の**冒頭**に置く。薄い代替案で数を埋めること、日次の本数に合わせるためにゲートを下げること、見た目のラベルを変えただけで同じ確認項目に落ちた Agent を数え直すことは、いずれも認めない。
- 基準を落とさない直し方は次の2通りである。同じ場面に属する薄い Agent 同士を1本の場面 Agent にまとめる（元の Agent は削除せず、アーカイブとして残す）。あるいは、不合格になった案に実在するコンテンツ集合や複数段階の流れを足して厚みを持たせ、ビルド済みファイルから全項目を再確認する。

## 本書のバージョン管理

本書は、セマンティックバージョニングでその場で育てていく。

- **patch**（1.0.x）：文面の修正、根拠となる事例の追加、同型を見分ける手がかりの追加。
- **minor**（1.x.0）：確認項目の追加、数える対象となる主張の種類の追加、不合格となる事例の追加。
- **major**（x.0.0）：ゲートそのものの変更（何をもって合格とするかが変わる）。

変更のたびに、次をすべて同じ作業の中で行う。冒頭の `version:` を上げる。下の変更履歴に1件追加する（日付、その変更を促した製作の実例、何を変えたか）。インストール済みのミラー `~/workspace/custom-skills/rokid_boutique_acceptance/SKILL.md` を更新する。そのうえで、両方を1つのコミットにまとめてプッシュする。検収に限らず製作全般に効く教訓は、本書に重ねて書かず、`rokid-agent-sop` に入れる。
