# Rokid Boutique Batch Acceptance

[中文](SKILL.md) | [English](SKILL.en.md) | 日本語
中文版（2026-10-29 時点）からの翻訳。齟齬がある場合は中文版が優先する。

ブティックラインの検収レイヤーである。生産（3つのゲート、9ステップの SOP、パッキング／プレビュー／README／GitHub 同期）は `rokid-agent-sop` にあり、この skill が加えるのは、完成したバッチを*どのように検証するか*だけである。バッチは、その**ビルド済みファイル**から検収する。台帳、PLAN のメモ、あるいは自身のレポートからは決して検収しない。主張は、ビルド済みプロジェクトが同じ事実を示して初めて成立する。

実行するタイミングは、ビルドの後、パッキングを完了と数える**前**、プッシュの前、そしてバッチを登録する（ルート README のリスト、PLAN の表、目標のタイムライン）前である。ブティックラインの日次 cron（`rokid-boutique-daily-10`）の本文には、これらのチェックの要約版が含まれている。両者が食い違う場合は、この skill が優先する。

## ビルド済みファイルから構造をチェックする

- 各 Agent について、ビルド済みプロジェクトファイル（`app.json` のページリスト + `pages/` ツリー）からページ数を数え、その数を Agent 名の横に記録する。
- ページが1つしかない非ゲーム Agent は不合格とする。1ページでは「入る → 進める → 結果」を担えないためである。（ゲームは SOP のループゲートの緩和に従うが、ブティックのゲームには依然として厚みが必要である。レベル／進行／コンテンツ集合がファイル内に存在しなければならない。）
- バッチ全体でページリストとビルド済みファイルのサイズを比較し、ラベルだけを変えて同じ骨格を共有する Agent を**同型 ― 不合格**としてフラグを立てる。ほぼ同一の `.ink` サイズが10個並ぶのは偶然ではなく証拠である。
- 台帳の主張や設計メモはすべて、ビルド済みファイルが同じ事実を示すまでは未証明として扱う。
- **ヘビー Agent ― 異なるページを数える。** ヘビーと指定された Agent（日次バッチには2つ含まれる）は、ビルド済みファイル内に**20以上の異なるページ**を示さなければならない。`app.json` のページリストと `pages/` ツリーを突き合わせ、1エントリにつき1ページとし、すべてのページが内容と配線の両面で機能的に異なっていなければならない。1ページの状態違い、デモのステップ、スクリーンショットのバリエーションはページとして数えない。5ページを抜き取りチェックして本当に異なるかを確認し、似たページは数える際に統合して合計を再確認する。統合後に20未満であれば不合格とし、数えない。

## 主張された各ゲートをコードで検証する

- **コンテンツ集合 ― 数える。** 主張された集合ごとに、ビルド済みファイル内の項目を数えてその数を記録する（駅、曲、問題、屋台、手順など）。数えられない集合は存在しない。
- **ループ ― 呼び出しを探す。** 主張されたループのステップごとに、そのステップに必要な API 呼び出しをビルド済みファイルから探す（頭部の向き／`onHeadGesture`、ASR、TTS、カメラなど）。呼び出しのないステップは配線されておらず、その主張は不合格となる。`app.json`／`package.json` の権限は、実際に配線された機能と一致しなければならない。カメラ／センサー機能に対して権限ゼロを主張してはならない。
- **セッションをまたぐ記憶 ― 永続化コードを探す。** セッションをまたぐ記憶が主張されている場合は、ストレージ／書き込みコードを探す（キー名を記録する）。永続化コードがなければ、その主張は成立しない。
- **エラーコード配線 ― grep する。** エラーコード連携を主張する Agent（新しいブティック Agent では必須）については、ビルド済みファイルからエラーコード配線を探す。ユーザーが目にするすべての失敗パスは、リポジトリルートの `ERROR-CODES.md` に従って、裸の形式（`E####`）のグローバルコードを表示し、`lastError`（完全なコード + slug + バージョン + 原文）を永続化しなければならず、README には使用するコードを列挙した「错误码」セクションがなければならない。コードなしで生のエラーテキストを表示する失敗パスは不合格である。また、ビルド済みファイルに対して `FileReader` を grep する。1件でもヒットすれば自動的に不合格である（この API は Ink ランタイムには存在せず、実機報告 E2005 で証明されている）。
- **API リスト準拠 ― 一括 grep し、呼び出しをたどる。** すべての Agent について、SOP の API 規律のレッスンで定義された不在リスト一括対象と旧式パターンをビルド済みファイルから grep する（`FileReader`、`sessionStorage`、`XMLHttpRequest`、`URL.createObjectURL`、`DOMParser`、`structuredClone`、`queueMicrotask`、`Notification`、クリップボード API、オブザーバーのペア、`ServiceWorker`、`new Worker(`、`canvas.toDataURL`、`captureStream`、`getDisplayMedia`、`applyConstraints`、`TextDetector`、`onclick=`、`Page(`、`App(`、`Widget(`、`require(`、旧式の `workers` フィールド ― 完全なリストは `rokid-agent-sop/SKILL.md` のルール2とその `API-AUDIT.md` にある）。1件でもヒットすれば**自動的に不合格**である。これらの API は公式リファレンスに存在しないことが確認されているため、その存在は、実機でのみ失敗するブラウザの習慣によるコードを意味する。次に、ビルド済みファイル内の自明でないすべての API 呼び出しを、その公式リファレンスエントリ（aiui-dev の `references/apis/` または上流の `documentation/3-api/`）まで抜き取りでたどる。たどれない呼び出しがある場合、その Agent の配線の主張は不合格となる。バージョン依存の API（Ink 0.15–0.19 で到達したもの。表は `API-AUDIT.md` にある）には、存在ガード（`typeof` ／ `wx.canIUse()`）がなければならない。
- **プレースホルダはプレースホルダとして明示する。** プレースホルダやサンプルの機能は、インターフェースとメモの両方でプレースホルダと明示し、配線済みとしては決して数えない。

## 合格したものだけを数え、残りを報告する

- Agent は、上記のチェックに対して、その Agent が行うすべての主張が合格した場合にのみバッチに数える。
- 不合格となった Agent はそれぞれ、不合格となったチェックとビルド済みファイルの証拠とともに報告し、バッチの不足分はレポートの**冒頭**に置く。薄い代替品で数を埋めてはならず、日次の数に到達するためにゲートを下げてはならず、表面的なラベル変更の後に同じチェックで不合格となった Agent を数え直してはならない。
- 基準を保つ是正策：1つのシナリオに属する薄い Agent 同士を1つのシナリオ Agent に統合する（元のものはアーカイブしたまま残し、決して削除しない）、あるいは不合格となったコンセプトに本物のコンテンツ集合／複数ステップのフローを加えて厚みを持たせ、ビルド済みファイルからすべてのチェックを再実行する。

## この skill のバージョニング

この skill はその場で、セマンティックバージョニングにより反復する。

- **patch**（1.0.x）：文言の修正、証拠の例の追加、同型性を見抜く新しい手がかり。
- **minor**（1.x.0）：新しいチェック、新しい「数えられる主張」の種類、新しい不合格ケース。
- **major**（x.0.0）：ゲートレベルの変更（合格と数えられるものの意味が変わる）。

変更のたびに：上記の `version:` を上げ、下記に変更履歴のエントリを追加し（日付、どの生産実行から学んだか、何が変わったか）、同じターンでインストール済みのミラー `~/workspace/custom-skills/rokid_boutique_acceptance/SKILL.md` を更新し、両方を1つのコミットでプッシュする。すべての生産に当てはまる教訓（検収だけに限らないもの）は、ここに重複させるのではなく、代わりに `rokid-agent-sop` に入れる。
