# Rokid 指向性設計
[中文](SKILL.md) | [English](SKILL.en.md) | 日本語
中文版（2026-10-29 時点）からの翻訳。齟齬がある場合は中文版が優先する。

DI エージェント向けの設計レイヤー。共通の制作パイプライン（能力のレッドライン、統治する三つの関門、9ステップの SOP、pack/preview/README/GitHub 同期）は `rokid-agent-sop` にある。本スキルは指向性シリーズ固有のものだけを追加する。すなわち、DI エージェントをどう出荷するかではなく、どう構想し、どうチェックするかである。エージェントが DI といえるのは、次の三つをすべて満たす場合のみである。DI 番号があること、プロジェクトが `directional/<slug>/` 配下にあること、少なくとも二つの指向性プリミティブを使って下記の創設テストに合格すること（シリーズ PLAN は 2 個以上を要求し、エージェントの README に明記する）。

## 「指向性」とは何か — 創設テスト（立項時にまず問う）

グラスと胸装着型 AI デバイス（あるいはスマートフォン）の根本的な違いは幾何学にある。**カメラは装着者の視線と同軸であり、頭の向きが注意のポインタであり、ディスプレイは視野の中にある。** 胸装着デバイスは、ユーザーが何を見ているかも、注意がどこにあるかも分からず、邪魔をする方法でしか情報を返せない。DI のコンセプトはすべて、設計の前に次の三つの問いに答える。

1. **「見て指す」を取り除いても、このエージェントは成り立つか。** タップやリストやメニューで同じように動くなら、指向性は装飾にすぎない。DI エージェントではない。
2. **スマートフォンや胸装着デバイスでそのまま置き換えられるか。** 置き換えられるなら、グラスの前提が使われていない。コンセプトを却下するか、幾何学を中心に設計し直すこと（何に向き合っているか、どこに立っているか、頭が何をしているか）。
3. **この場面は、絶対位置や基点方位を知ることで利点を得るか。**（車を探す、帰還、集合地点、屋外。）利点があるなら、`GEOLOCATION` は最初から最小権限セットに入れ、目的を明示して宣言する（下記 GEO を参照）。場所に固定されたタスクを相対方向だけの案内に無理に押し込めず、後から GPS を付け足してもいけない。

## 設計プリミティブ（設計の基本要素）

- **GAZE — 見て指す。** カメラの視野中心がそのまま視点である。見ることが、指すこと、タップすること、フレーミングの代わりになる。`ImageCapture.takePhoto({mode})` は、遠くの小さな文字には `telephoto`、バーコードや広い視野には `wide`、汎用には `default` を使う。手で選択することは決してしない。
- **HEAD — 方位登録と相対方向。** `AbsoluteOrientationSensor` のクォータニオンから yaw を求め、`onOrientationStabilityChange`（頭が静止した状態）と `onHeadGesture('nod')` を使う。**`'nod'` はドキュメントに記載された唯一のジェスチャ値である**。shake/turn/tilt のジェスチャイベントを前提に設計してはいけない。その場の方向は常に**相対方向**である。目標方位から現在方位を引いたもので、**+ は右側**を意味し、「左前方 35°」のように発話する。（基点方位はもう一方のレジスタに属する。下記 GEO を参照。役割分担はそこで明示する。）
- **Dwell = 視線による確認（凝視確認）。** 頭がコーン内（通常は ±15°）で持続時間（約1〜2秒、tick で累積）静止することが、そのまま確認になる。対象を見直すことが了承であり、注意がループを閉じるのであって、ボタンではない。速く通り過ぎただけでは数えず、コーンから出たら持続時間はリスタートする。
- **MIC アレイ — 正直な位置づけ。** 4マイクアレイの `microphoneMode`（`wearer` / `far-field` / `near-field` / `omnidirectional`）は、設定された `getUserMedia` ストリームだけを形作る。DI の設計においてマイクモードのストリームは次の二つのうちの一つである。**可用性チェック**（開いて、`track.getSettings()` でモードを読み戻し、直ちにトラックを停止する）か、**レベルメーターへの供給**（Web Audio の `AnalyserNode` による RMS）である。ホストの `SpeechRecognition` はホスト自身のマイクで動作する。モードが認識のノイズ除去、優先順位付け、整形をすることは決してない。UI はチェック結果を専用の `MIC CHECK:` 行に保持し、聞き取りには `(host ASR)` とラベルを付ける。
- **SCAN — 頭を回して音を探す。** 音の到来角度を取得する API は存在しない。音の位置は、頭をゆっくり回しながらサンプリングしたマイクの**レベルと方位の組み合わせ**である。最も大きいレベルが得られた方位が音のある場所である。ビームフォーミングの角度を提示してはならず、レベルはレベルでしかない。音が何であるかを主張してはならない（分類機能は存在しない）。
- **GEO — GPS：基点方位と位置**（GO、2026-10-28：「指向性では GPS 情報を活用し、東西南北と具体的な位置を知ること」）。`GEOLOCATION` はプラットフォームの七つの権限名の一つである（完全な表は SOP のレッドラインにある）。設計で位置を使う場合は、目的を明示して宣言する（公開時のレッドライン）。方向には**二つのレジスタ**があり、設計の腕は正しい方を選ぶことにある。
  - **相対方向**（目標から現在方位を引いたもの、+ は右）は、**振り向いて向き合えるものへのその場の案内**に使う。初期フリートの「基点方位は使わない」という習慣は、この言い方、つまり視野内の案内に関するルールであり、**基点方位の禁止ではない**。
  - **基点方位と位置**は、**場所に固定されたタスク**に使う。何かがどこにあるかを知ること（北 / 北西）、保存した地点までの距離、駐車した車への帰還、集合地点、自宅などであり、「車は北西方向に約300メートル」のように案内する。タスクが絶対的な場所に関するものなら、GPS と基点方位が最初から設計そのものである。
  - **フリートの位置パターン**：その場所に立って地点を保存する（GPS の測位と任意で方位）。帰還案内は、新しい測位から方位と距離を**再計算**して行う。連続更新が重要な場合は `watchPosition` を使い（DI42 `transit-direction` のパターン）、そうでない場合はワンショット測位を使う。測位の精度と古さは常に正直に表示し、精度をでっち上げる代わりに「測位が不正確 / 信号なし」の状態に劣化させる。**GPS は屋内では弱い。そのことを脚注の言い訳ではなく、設計の中で明示する。**
  - **方位の正直さ**：基点方位は、デバイスの絶対方位参照がどれだけ信頼できるかによってのみ決まる。その参照がデバイス上で信頼できない場合、設計は相対案内に劣化させ、**その理由を述べる**。測位を偽装してはならず、距離を丸めて偽の精度にしてはならない（±50 m の測位からは「約300メートル」と言い、「287メートル」とは決して言わない）。

## 能力に関する正直さの境界（監査基準 — 2026-10-24 の監査より、交渉不可）

DI01〜DI37 の監査では、コードレベルでの組織的な捏造は見つからなかった（仕組み違反はちょうど1件）。その他の違反はすべてコピー文面にあった。コピーと設計の両方が守るべきラインは次のとおりである。

- **アイトラッキングはない。**「視線」はどこでも常に頭の向きである。
- **OCR API はない。** 文字を読むとは、望遠写真と LLM の画像入力の組み合わせである（ドシエ §2.9：`image_url` パーツ、data: URL を含む、user ロールのみ、先に `availability()`、後に `destroy()`）。Data-URL の画像入力がドキュメントに記載された経路である（公式の LanguageModel の例は、まさにこのために `blob.arrayBuffer()` とチャンク分割した `btoa` を手書きしている）。`FileReader` はこのランタイムには一切存在しない。実機で証明済みであり、SOP の API 規律の教訓によって禁止されている。画像経路のデバイス動作は依然として**実機未検証**であるため、画像経路を使う設計はすべて、完全に使える非画像のフォールバック（装着者自身の音声入力 / 手入力）を保持し、これを未検証項目の先頭に挙げる。鏡像の主張も同じく禁止である。「写真は LLM に届かない」は*偽のプラットフォーム主張*である（5台のエージェントのドキュメントに掲載され、訂正された）。テキストだけを送る設計は「テキストのみ。製品上の選択」と述べる。
- **マイクモードはホスト ASR に触れることはない**（上記 MIC を参照）。フリートの6台のコピーがまさにこの継ぎ目を破っており、監査で最も繰り返し指摘された項目である。
- **音の分類も音の定位もない。** SCAN とレベルだけの言い方が、正直なツールキットのすべてである。
- **顔認識はない。**「人物を認識する」とは、その人のバッジの文字を読むこと（DI47 `badge-reader`）か、装着者が登録した方位と照合することであり、顔によるものでは決してない。
- **写真は永続化されない。** このランタイムでは Blob を保存できない。永続化するのは装着者が確認した**テキスト**のみであり、写真を撮る場所ではどこでも「写真は保存されない」と明示する（DI22 / DI29 のコピーは、コードが破棄した写真をアーカイブしたと主張していたため、改訂された）。
- **TTS の `lang` は効かない**（固定の11音声）。`utterance.lang` を設定してはならない。ASR の `rec.lang` は実在する別のプロパティである。
- **ホスト LLM の場所は公開されていない。**「オンデバイス AI」と主張してはならない（DI24 のコピーが主張していたため、改訂された）。
- **バックグラウンドでの存在はない。** タイマー、リマインダー、ウォッチャーは、エージェントが開いている間だけ存在する。該当する場所では常に画面上の1行でその旨を表示する。**エージェント同士は呼び出せない**（`openAgent` はなく、`window.open` は他のエージェントを開けない）。ルーターやマルチエージェントの設計はしない。
- **プラットフォームに関する主張は、そのエージェントだけでなく、プラットフォームについて真でなければならない。** DI33 は姿勢センサーを「唯一のモーションの基盤」と呼んだ（Accelerometer と Gyroscope はドキュメントに記載された API である）が、実装されたルール（3秒以内に60°）とは異なる判定ルール（240°/s）を印刷していた。UI に記載するルールは実装されたルールそのものである。
- **健康と安全に関するコピーはリマインダーの枠組みのみ**であり、効能を主張してはならない（DI32）。

## パターンライブラリ（再利用パターン集）

- **方位登録簿。** 対象に一度向き合い、その方位を（音声入力したラベルとともに）紐づける。以後はエージェントが相対方向でそれを指し示す（DI07 `find-my-thing`、DI28 `home-patrol`、注意力の WATCH グループ全体）。方位の読み取りがなければ登録は正直に拒否し、方向をでっち上げることは決してない。登録は、登録したときに立っていた場所に固定される。その旨を明示すること。
- **振り返り確認。** アラート（タイマー終了、状態変化）は**一度だけ**、相対方向の言い方で発話し、ユーザーが振り向いて対象に dwell する（顔による了承）かタップするまでバナーを残す。指向性シリーズの象徴的な閉ループである。
- **読み取り相互照合。** 機械による読み取り（写真から LLM）と装着者自身が音声入力した版を、正規化した文字どおりで比較し、MATCH ✓ / DIFF ⚠ とする。DIFF の場合は**装着者の版が優先**し、それが出典であることをアナウンスする（DI41 `sign-reader`、DI47 `badge-reader`）。機械が読んだものは未確認のまま保存することは決してない（DI39 `board-capture` の保持のみのファイリング）。
- **相対コースロック。** *現在*の方位をコースの原点としてロックする。純粋に相対的であり、ドキュメントに記載されていない yaw のゼロ点を回避する。しきい値を超えた持続的なドリフトには、エピソードごとに**一度だけ**音声で訂正を伝え、狭いバンド内に戻ったら再び有効化する（DI42 `transit-direction`。そのハーネスは実際のバグを捉えた。目的地が START の原点ではなく移動する測位に固定されていたため、距離が縮まらなかった）。
- **答えの隔離。** 読み取りによって、装着者がうっかり目にしてはならないもの（答え）が生じた場合は、明示的な表示操作の背後にゲートする。答えの行をパースレベルで除去し、デフォルトで表示せず、nod では決して表示しない（DI40 `homework-lens`）。
- **DEMO シードの規律。** デモ状態は、**一つの** Date スナップショットから純粋な文字列として描画して導出する。プレビューホストの仮想化された時計はサンプル間でドリフトする。Dwell とカウントダウンのタイマーは tick を累積し、時計を再サンプリングすることは決してない。DEMO は実際の状態を正確に復元し、実際のストレージには何も書かない。

## DI 制作レッスン（SOP への追加）

- **ジェスチャ優先**（GO の裁定、ドシエ §3.2.1）：テンプルのシングルタップは確認、ダブルタップは戻る、スワイプはスクロール。頭の静止と nod をメインフローに組み込み、画面上のボタンは最小限にする。デバイスの教訓として、bindtap のみのボタンはグラス上でトリガーできない。ページ自身がキーを対応づける（`onKeyDown`）。各エージェントの実機テスト時にその配線を確認する。すべての README にジェスチャ対応の節を記載する。
- **短い1行のステータス文字列**（最大で約60文字）：長い折り返しテキストはコントロールを下に押し下げ、スクリプト化されたプレビュークリックを壊す。プレビューホストはオフセットした帯でボタンをヒットテストする。レイアウト状態ごとにヒット座標を調べ、描画された中心を信用してはならない。
- **Tick 演算。** すべてのタイミング（カウントダウン、dwell、ドリフトのエピソード）は、固定頻度のエンジンの tick を累積する。繰り返しの実時計サンプリングから時間を計算してはならない。プレビューの時計はドリフトし、この習慣はハーネスが後で捉えなければならない競合バグを隠してしまう。
- **パックの前にハーネス。** コアロジックは wx をスタブ化した Node ハーネスで実行し、アサーション数をエージェントとともに報告する（フリートの範囲は55〜154）。パックは**最後**に行い、README が最終になった後に行い、パック内容を `aix list` で確認する。完全なパイプラインは `rokid-agent-sop` のものである。これは決して省略してはならない1行である。
- レイアウト：本体は `directional/<slug>/` と `aix/<slug>.aix` と `screenshots/<slug>/`。ブランチ `agent-<slug>` のルートにはエージェントの7ファイルちょうどを置く。本体の README は `../../screenshots/<slug>/…` を埋め込む。

## 形式とロスター

- 番号の権威：`~/workspace/goals/50-agent-rokid-aiui/files/PLAN-50-Agents.md`。DI01〜DI50 は構築、プッシュ、検証が済んでいる（シリーズは2026-10-24 に完了）。ルート README のリストにおける DI シリーズのバッジは指向性である（バッジの定義は凍結されている。SOP を参照）。
- DI42 以降は最初からジェスチャ優先で構築された。それ以前のエージェントのフリート全体の UI 統一は、GO の実機テストがインタラクションを定義するまで**意図的に延期**されている（MVP の裁定）。UI の作り直しで先取りしてはならない。
- DI エージェントは、フリートの中で内蔵能力（慧眼識別 / ナビゲーション / プロンプター / 文字起こし）に最も近い隣人である。新しい DI コンセプトは、まず `rokid-conflict-audit` に通すこと。2026-10-25 の監査では、14件の第1階層の競合のうち10件がこのシリーズにあった。本体が内蔵機能そのものである指向性コンセプトは除外され、SOP の統治ルールにより、再編成も提出もしない。

## このスキルのバージョニング

このスキルはその場でイテレーションし、semver を使う。

- **patch**（1.0.x）：文言の修正、例の追加、エージェントごとのメモの追加。
- **minor**（1.x.0）：新しい再利用パターン、新しい制作レッスン、ロスターや状態の更新。
- **major**（x.0.0）：創設テスト、プリミティブ、正直さの境界の変更。その場合、出荷済みのすべての DI エージェントの README とコピーを、それに対して再確認しなければならない。（境界の明確化が実際にはどのようなものか：DI02 の shake 分岐の削除と、2026-10-24 の監査後に Build 1.0.1 に改訂された14台のエージェント。）

変更のたびに、上の `version:` を上げ、下に変更ログのエントリを追加し（日付、制作の実行から何を学んだか、何が変わったか）、同じターンでインストール済みミラー `~/workspace/custom-skills/rokid-directional/SKILL.md` を更新し、両方を一つのコミットでプッシュする。すべてのエージェントに当てはまる教訓（DI だけではない）は、代わりに `rokid-agent-sop` に入れる。ここに重複させてはならない。
