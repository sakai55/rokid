# Rokid 指向性設計
[中文](SKILL.md) | [English](SKILL.en.md) | 日本語
本書は中文版（2026-10-29 時点）を正本とする。解釈に食い違いが生じた場合は中文版を優先する。

DI エージェントの設計を扱うレイヤーである。制作の共通手順――能力のレッドライン、統治ルールである三つの関門、9ステップの SOP、pack / preview / README / GitHub 同期――は `rokid-agent-sop` に集約されている。ここでは指向性シリーズ固有の内容だけを扱う。対象は出荷手順ではなく、DI エージェントをどう企画し、どう検証するかである。DI と呼べるのは、次の3点をすべて満たすものに限る。DI 番号を持つこと。プロジェクトが `directional/<slug>/` 以下にあること。下記の立項テストに合格し、指向性プリミティブを2つ以上使っていること（シリーズ PLAN の要件であり、使うプリミティブは当該エージェントの README に明記する）。

## 「指向性」とは何か — 立項テスト（最初に問うこと）

グラスと胸装着型 AI デバイス（あるいはスマートフォン）の違いは、性能ではなく幾何学にある。**カメラは装着者の視線と同軸にあり、頭の向きがそのまま注意のポインタになり、ディスプレイは視野の中にある。** 胸装着デバイスは、装着者が何を見ているかも、注意がどこに向いているかも知ることができない。情報を返すにも、装着者の作業を遮るしかない。DI の企画は、設計に入る前に次の3問へ答えなければならない。

1. **「見れば指せる」を取り除いても成立するか。** タップやリスト、メニューで同等に動くのであれば、指向性は飾りでしかない。その企画は DI ではない。
2. **スマートフォンや胸装着デバイスでそのまま代替できないか。** 代替できるなら、グラスである必然性を使えていない。企画を却下するか、幾何学――何に向いているか、どこに立っているか、頭がどう動くか――を核に据えて設計し直すこと。
3. **絶対位置や方位（東西南北）を知ることで、この場面は良くなるか。**（車を探す、来た道を戻る、集合地点、屋外での利用が典型である。）良くなるなら、`GEOLOCATION` を最初から最小権限セットに入れ、用途を明示して宣言する（後述の GEO を参照）。場所に紐づくタスクを相対方向だけの案内に押し込めてはならない。GPS を後付けにすることも禁止である。

## 設計プリミティブ

- **GAZE — 見ることが指すことになる。** カメラの画角の中心が、そのまま視点である。見る行為が、指差し、タップ、フレーミングを置き換える。`ImageCapture.takePhoto({mode})` のモードは、遠方の小さな文字には `telephoto`、バーコードや広範囲の撮影には `wide`、通常用途には `default` を選ぶ。選択操作に手は使わない。
- **HEAD — 方位の登録と相対方向。** `AbsoluteOrientationSensor` のクォータニオンから yaw を求め、頭が静止したことを `onOrientationStabilityChange` で、うなずきを `onHeadGesture('nod')` で受け取る。**ドキュメント化されているジェスチャ値は `'nod'` のみである。** shake / turn / tilt のジェスチャイベントが来る前提で設計してはならない。案内に使う方向は常に**相対方向**である。目標の方位から現在の方位を引いた値で、**プラスが右**を表し、「左前方 35°」のように読み上げる。（東西南北で表す方位は、もう一方の方式に属する。使い分けは後述の GEO で定義する。）
- **Dwell = 注視による確定（凝視確認）。** 頭があるコーンの内側（目安は ±15°）で一定時間（約1〜2秒、tick の積算で数える）静止したら、それを確定とみなす。対象を見直す行為そのものが了承になる。ループを閉じるのはボタンではなく注意である。コーンを素早く横切っただけでは数えない。コーンの外へ出たら、継続時間はゼロから数え直す。
- **MIC アレイ — 正直な位置づけ。** 4マイクアレイの `microphoneMode`（`wearer` / `far-field` / `near-field` / `omnidirectional`）が影響するのは、それを設定した `getUserMedia` ストリームだけである。DI の設計でマイクモードのストリームが担う役割は、次のどちらかしかない。**利用可否のチェック**（ストリームを開き、`track.getSettings()` でモードを読み戻して、直ちにトラックを止める）か、**レベルメーターへの入力**（Web Audio の `AnalyserNode` で RMS を取る）かである。ホストの `SpeechRecognition` はホスト側のマイクで動く。モードが音声認識のノイズ除去や優先順位付け、整形を行うことはない。UI ではチェック結果を専用の `MIC CHECK:` 行に出し、聞き取り中であることには `(host ASR)` と表示する。
- **SCAN — 頭を回して音源を探す。** 音の到来方向を返す API は存在しない。音源の位置は、頭をゆっくり回しながらマイクの**レベルと方位**をサンプリングし、レベルが最も大きくなった方位として推定する。ビームフォーミングによる角度であるかのように見せてはならない。また、レベルから分かるのは大きさだけであり、その音が何であるかまで主張してはならない（音の分類機能は存在しない）。
- **GEO — GPS が担う方位と位置**（GO、2026-10-28：「指向性では GPS 情報を活用し、東西南北と具体的な位置を知ること」）。`GEOLOCATION` は、プラットフォームに定められた7つの権限名の1つである（全表は SOP のレッドラインにある）。位置を使う設計では、公開時のレッドラインに従い、用途を明示して宣言する。方向の表し方には**2つの方式**があり、どちらを選ぶかが設計の要点になる。
  - **相対方向**（目標の方位 − 現在の方位、プラスが右）は、**振り向けば対象に向き合える場面での、その場の案内**に使う。初期のフリートにあった「方位（東西南北）は使わない」という慣行は、この言い方、つまり視野内での案内についてのルールであって、**方位そのものの禁止ではない**。
  - **方位と位置**を使うのは、**場所に紐づくタスク**である。対象がどこにあるか（北 / 北西）を伝える、保存した地点までの距離を出す、駐車した車まで戻る、集合地点や自宅へ案内する、といった用途が該当し、「車は北西方向におよそ300メートル先」のように案内する。タスクの本質が絶対的な場所にあるなら、GPS と方位は後付けの機能ではなく、最初から設計の中心である。
  - **フリートで確立した位置のパターン**：地点の保存は、その場所に立って行う（GPS の測位に、必要に応じて方位を添える）。帰還の案内は、測位のたびに方位と距離を**再計算**する。継続的な更新が必要なら `watchPosition` を使い（DI42 `transit-direction` のパターン）、不要ならワンショットの測位で済ませる。測位の精度と鮮度は常に正直に表示し、精度があるかのように見せかけない。「測位が不正確 / 信号なし」といった劣化状態を出すこと。**GPS は屋内では弱い。この制約は脚注で済ませず、設計の中に明記する。**
  - **方位の正直さ**：方位による案内の確かさは、デバイスの絶対方位の基準がどれだけ信頼できるかで決まる。その基準を実機で信頼できない場合は、相対方向の案内に落とし、**なぜ落としたかを明記する**。測位結果を捏造してはならない。距離を丸める際も、実在しない精度を装ってはならない（精度 ±50 m の測位なら「およそ300メートル」であり、「287メートル」とは決して言わない）。

## 能力表示の境界（監査基準 — 2026-10-24 監査より、交渉の余地なし）

DI01〜DI37 の監査では、コードレベルでの組織的な捏造は見つからなかった（仕組みそのものの違反は1件のみ）。残りの違反はすべて文面側にあった。文面と設計の双方が守るべき境界は、次のとおりである。

- **アイトラッキングはない。**「視線」と書く場合、それは常に頭の向きを指す。例外はない。
- **OCR API はない。** 文字を読む処理は、望遠での撮影と LLM への画像入力で構成する（能力原子登録表の C3014–C3018：`image_url` パーツ、data: URL を含む、user ロールのみ、事前に `availability()` を確認し、使い終わったら `destroy()` を呼ぶ）。data URL による画像入力こそが、ドキュメント化された正規の経路である（公式の LanguageModel のサンプルは、まさにこの処理のために `blob.arrayBuffer()` とチャンク分割した `btoa` を手書きしている）。`FileReader` はこのランタイムには存在しない。実機で確認済みの事実であり、SOP の API 規律でも禁止されている。一方、画像経路のデバイス上の挙動は**実機未検証**である。したがって画像経路を使う設計は、画像なしでも完結する代替手段（装着者自身の音声入力や手入力）を必ず備え、その旨を未検証項目の先頭に書く。逆方向の誤りも禁止である。「写真は LLM に渡せない」は*プラットフォームについての虚偽の説明*であり（実際に5台のエージェントの文書へ混入し、訂正された）、テキストのみを送る設計であれば「テキストのみとする。これは製品上の選択である」と書く。
- **マイクモードはホスト ASR に一切関与しない**（前述の MIC を参照）。フリートの6台がまさにこの継ぎ目で文面を誤っており、監査で最も多く繰り返された指摘である。
- **音の分類も、音源定位もできない。** 正直に使える手段は、SCAN とレベルだけに基づく表現に限られる。
- **顔認識はない。**「人物を認識する」とは、相手のバッジに書かれた文字を読むこと（DI47 `badge-reader`）、または装着者が登録した方位と照合することであり、顔による識別ではない。
- **写真は永続化しない。** このランタイムでは Blob を保存できない。永続化できるのは、装着者が確認した**テキスト**だけである。写真を撮る画面では、必ず「写真は保存されません」と明示する（DI22 / DI29 の文面は、コードが破棄している写真を保存したかのように書いていたため改訂した）。
- **TTS の `lang` は効かない**（音声は固定の11種）。`utterance.lang` を設定してはならない。ASR 側の `rec.lang` は、これとは別の実在するプロパティである。
- **ホスト LLM がどこで動いているかは公開されていない。**「オンデバイス AI」と主張してはならない（DI24 の文面が主張していたため改訂した）。
- **バックグラウンドでは存在しない。** タイマー、リマインダー、監視の類は、エージェントを開いている間にしか動かない。該当する画面には、その旨を常時1行で表示する。**エージェント同士は呼び出せない**（`openAgent` は存在せず、`window.open` で別のエージェントを開くこともできない）。ルーター型やマルチエージェント型の設計は行わない。
- **プラットフォームについての説明は、当該エージェントだけでなく、プラットフォーム全体について正しくなければならない。** DI33 は姿勢センサーを「唯一のモーション基盤」と書いた（Accelerometer と Gyroscope もドキュメント化された API である）。さらに、実装した判定条件（3秒以内に60°）とは異なる条件（240°/s）を UI に表示していた。UI に書くルールは、実装したルールそのものでなければならない。
- **健康・安全に関する文面は、リマインダーとしての表現に限る。** 効能をうたってはならない（DI32）。

## パターンライブラリ（再利用パターン集）

- **方位登録簿。** 対象に一度向き合い、その方位を音声で入力したラベルとともに登録する。以後、エージェントは相対方向でその対象を案内する（DI07 `find-my-thing`、DI28 `home-patrol`、注意力シリーズの WATCH グループ全体がこの形である）。方位を読み取れなければ登録はできないものとして正直に拒否し、方向を捏造してはならない。登録した方位は、登録時に立っていた場所を基準にしている。その点も明記すること。
- **振り返り確認。** アラート（タイマーの終了、状態の変化）は、相対方向の表現で**1回だけ**読み上げる。その後は、ユーザーが振り向いて対象に注視する（顔を向けることによる了承）か、タップするまでバナーを残す。これが指向性シリーズを象徴する閉ループである。
- **読み取りの突き合わせ確認。** 機械の読み取り結果（写真 → LLM）と、装着者自身が音声で入力した内容を、正規化したうえで文字列として比較し、MATCH ✓ / DIFF ⚠ を出す。DIFF の場合は**装着者の入力を正**とし、その旨を読み上げる（DI41 `sign-reader`、DI47 `badge-reader`）。機械が読んだ内容は、確認を経ずに保存してはならない（DI39 `board-capture` の、保持だけを行うファイリングもこの考え方である）。
- **相対コースのロック。** *現在*の方位をコースの原点として固定する。完全に相対的な方式であり、ドキュメント化されていない yaw のゼロ点に依存せずに済む。しきい値を超えるドリフトが続いた場合は、そのエピソードにつき**1回だけ**音声で修正を伝え、狭い範囲内に戻ったら再び検出を有効にする（DI42 `transit-direction`。同エージェントのハーネスは実在のバグを検出した。目的地が START 時点の原点ではなく移動中の測位に固定されていたため、距離が縮まらなかった）。
- **答えの隔離。** 読み取りの結果に、装着者が偶然目にしてはならない内容（答え）が含まれる場合は、明示的な表示操作をしなければ見られないようにする。答えの行はパースの段階で取り除き、初期表示には決して出さず、nod で表示することもしない（DI40 `homework-lens`）。
- **DEMO シードの規律。** デモ用の状態は、**1つ**の Date スナップショットから、純粋な文字列として描画できる形で導出する。プレビューホストの仮想時計は、サンプリングのたびにずれるためである。dwell やカウントダウンのタイマーは tick を積算し、時計を再サンプリングしてはならない。DEMO は実状態を正確に復元し、実ストレージには何も書き込まない。

## DI 制作レッスン（SOP への上乗せ）

- **ジェスチャ優先**（GO の裁定、能力原子登録表の C8002–C8010）：テンプルのシングルタップが確定、ダブルタップが戻る、スワイプがスクロールである。頭の静止と nod をメインフローに組み込み、画面上のボタンは最小限に抑える。実機で得た教訓として、bindtap だけのボタンはグラス上では発火させられない。各ページが自らキーを割り当てる必要がある（`onKeyDown`）。エージェントごとの実機テストでは、この配線を確認すること。すべての README にジェスチャ対応表の節を置く。
- **ステータス文字列は短く、1行に収める**（目安は最大で約60文字）。長い折り返しテキストは操作要素を下へ押し下げ、スクリプトによるプレビューのクリックを壊す。プレビューホストは、ずらした帯状の領域でボタンのヒットテストを行う。レイアウトの状態ごとにヒット座標を実測し、描画上の中心を当てにしてはならない。
- **Tick 演算。** すべての時間管理（カウントダウン、dwell、ドリフトのエピソード）は、固定間隔のエンジンの tick を積算して行う。実時計を繰り返しサンプリングして経過時間を求めてはならない。プレビューの時計はずれるうえ、この習慣は競合バグを隠し、後段のハーネスに検出を押しつけることになる。
- **pack の前にハーネスを通す。** コアロジックには、wx をスタブ化した Node ハーネスを用意して実行し、アサーション数をエージェントとともに報告する（フリートでの実績は55〜154）。pack は**最後**に行う。README が確定した後に実施し、パックの中身を `aix list` で確認する。パイプライン全体は `rokid-agent-sop` の担当である。ここの1行だけは、決して飛ばしてはならない。
- レイアウト：本体は `directional/<slug>/` + `aix/<slug>.aix` + `screenshots/<slug>/` とし、ブランチ `agent-<slug>` のルートには当該エージェントの7ファイルだけを置く。本体の README には `../../screenshots/<slug>/…` を埋め込む。

## 形式とロスター

- 番号の正本：`~/workspace/goals/50-agent-rokid-aiui/files/PLAN-50-Agents.md`。DI01〜DI50 は構築、プッシュ、検証まで完了している（シリーズ完了は2026-10-24）。ルート README の一覧で DI シリーズに付くバッジは指向性である（バッジの定義は凍結されている。SOP を参照）。
- DI42 以降は、当初からジェスチャ優先で構築した。それ以前のエージェントについては、フリート全体の UI 統一を、GO の実機テストによってインタラクションの定義が固まるまで**意図的に見送っている**（MVP に関する裁定）。UI の作り直しで先回りしてはならない。
- DI エージェントは、フリートの中で標準搭載の能力（慧眼識別 / ナビゲーション / テレプロンプター / 文字起こし）に最も近い。新規の DI 企画は、まず `rokid-conflict-audit` にかけること。2026-10-25 の監査では、第1階層の競合14件のうち10件がこのシリーズに集中した。本体そのものが標準機能と重なる指向性企画は不採用であり、SOP の統治ルールにより、再編成しての提出も行わない。

## このスキルのバージョニング

このスキルは、同じ場所で改訂を重ね、semver で管理する。

- **patch**（1.0.x）：文言の修正、例の追加、エージェント単位の注記の追加。
- **minor**（1.x.0）：再利用パターンの追加、制作レッスンの追加、ロスターや状態の更新。
- **major**（x.0.0）：立項テスト、プリミティブ、能力表示の境界の変更。この場合は、出荷済みのすべての DI エージェントについて、README と文面を新しい内容に照らして再点検しなければならない。（境界の明確化とは実際には何か。例として、DI02 の shake 分岐の削除と、2026-10-24 の監査を受けて Build 1.0.1 へ改訂した14台が挙げられる。）

改訂のたびに、上部の `version:` を引き上げ、下部へ変更ログを1件追加する（日付、制作の実績から何を学んだか、何を変更したか）。あわせて、同じターンで導入済みミラーの `~/workspace/custom-skills/rokid-directional/SKILL.md` を更新し、両方を1つのコミットでプッシュする。DI に限らずすべてのエージェントに当てはまる教訓は、ここに重複して書かず、`rokid-agent-sop` 側へ入れる。
