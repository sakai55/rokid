# Rokid Agent Production SOP
[中文](SKILL.md) | [English](SKILL.en.md) | 日本語
本書は中文版（2026-10-29 時点）に準拠する。解釈に相違がある場合は中文版を正とする。

Agent は 1 件で 1 つのシナリオを完結させる（後述の基本ルールを参照。本ルールは「生活上の問題を 1 つ扱う」という従来の考え方に優先する）。手順は全 9 ステップ。ステップ 8 の登録まで終えて、初めて完成とする。

## 基本ルール — Agent 1 件につき完全なシナリオ 1 つ（GO、2026-10-26）

このルールは、Rokid の公式開発チームによる本リポジトリのレビューと、海外 Agent Store の掲載作全点（約 32 件）の分析を踏まえて定めたものである。作るのは「1 件で 1 シナリオ」だけ。「1 件で 1 機能」は作らない。公式側の評価は明確で、機能 1 点だけの小さな Agent はまず審査を通らず、通った例はほぼ見当たらない。シナリオが薄い Agent は、公開後にプラットフォーム側から停止措置を受けたり、ユーザーから苦情を受けたりするリスクも抱える。実際に Store で定着しているのは、プレイの一巡（ループ）が成立したゲーム、ハブ 1 つに束ねたコレクション（利用数 2 位はミニゲーム集）、「今日何を食べる／何を着る／どう鍛える」といった日常の意思決定を扱うシナリオ、実データに裏付けられたサービス、まとまったコンテンツセットであり、単発の動作だけで終わるものはない。

コンセプトは、ステップ 1 の設計に入る前に次の 3 ゲートをすべて通すこと。1 つでも落ちたら、その場で不採用とする。「とりあえず作って様子を見る」は認めない。

1. **シナリオゲート**: 誰が、いつ、なんのために開くのかを一文で言えるか。求めるのは「場面と目的」であって、動作や機能の名前ではない。一文で言えないコンセプトは作らない。
2. **ループゲート**: 入口 → 進行 → 結果（精算）に至る一巡があり、繰り返し使えるか。単発動作だけ、1 ページだけ、プロンプト 1 回だけの Agent は不可。例外はゲームのみ（Store での実績に基づく）。ゲームに限り、開始・勝敗・スコアを備えたプレイループが完結していれば、メカニクス 1 つでもよい。
3. **厚みゲート**: 実データソース／コンテンツセット／複数ステップのフロー／セッションをまたぐ記憶／コレクション型ハブのうち、2 つ以上を備えているか。端末の標準機能と中身が同じものは、その時点で不採用とする（競合監査の第 1 区分。組み直しての再提出もしない）。

実行ルール:

- **既存フリート（薄い Agent 170 件超）**: 1 件ずつ審査に出さない。削除もしない。扱いはシナリオ単位への再編に限る。同じシナリオの単機能 Agent は 1 件のシナリオ Agent にまとめ、まとめられないものはリポジトリに封存したまま残す。
- **提出順序**: 最初の提出は、ゲートを通した見本のみ。(1) 頭部ゲームのコレクションハブ。ゲーム全点を内蔵した単体の Agent として作る。Agent 同士は互いに呼び出せないため、ハブはルーターではなく「ゲームを内包した 1 件の Agent」である。(2) dabiaoge。見本のうち 1 件が審査を通り、実際の合格水準が見えるまでは、ほかの Agent を審査に出さない。
- **量産体制 — 2026-10-26 22:49、統一精品ラインへの移行に伴い廃止**: 旧来の日次バッチ cron 3 本（curb-cut / JP-KR / head-games、各 3 件/日）は廃止済み。現在は cron `rokid-boutique-daily-10` の 1 本だけを運用し、納品先はサイドチャット「做的就是精品」のみ。1 日 10 件を 5 方向（curb-cut（CC）、指向性、注意力、ゲーム（GA）、JP/KR ローカライズ）から作る。うち 5 件は「日本ローカル × 複合型」とし、日本の生活場面を舞台に（JP 番号、`japan/` 配下、日本語 UI）、curb-cut / 指向性 / 注意力 / ゲームのうち 2 方向以上を組み合わせる。日本ローカル単独、または 1 方向だけとの組み合わせは不可。残る 5 件は単一方向でも、2 方向以上の組み合わせでもよい。組み合わせる場合は、シナリオの中で自然に溶け込んでいること。機能を 2 つ並べただけの寄せ集めは認めない。旧 `rokid-agent-list-sync` cron（ルート README の Agent 一覧を 6 時間ごとに同期）も廃止済みで、一覧の更新は精品ラインの実行側が担う。その日のバッチを push した後、1 回だけ更新する。その締め作業には、後述のステップ 8 の注記と、MEMORY に記録されたバッジ凍結・凡例・退役 slug の各ルールが適用される。コンセプトはすべて事前に 3 ゲートを通す。落ちたものは、厚みを持たせて作り直すか不採用とし、判定結果を報告する。件数をそろえるために水準を下げることはしない。不足が出た場合は、コンセプトごとの判定とあわせて不足分を報告する。位置づけ（GO、2026-10-26 22:50）: 既存の 177 件は、可能性と能力の限界を探るための探索フリートであり、提出用の完成品ではない。精品ラインはその蓄積の上に立ち、検証済みの仕組みと教訓を引き継ぐ。薄い「1 機能 1 Agent」の形を繰り返してはならない。頭部ゲームのコレクションハブ（`head-games-hub`、機構は GA27–GA40 を予約）は前記のとおり提出見本の位置づけを維持する。精品ラインが、GO の指示なく予約済みの GA 番号を単体ゲームに流用することもしない。
- **実機テストのゲートは従来どおり**: 審査提出は、GO の実機テストが完了し、GO が「真机测试完成了」と明言した後に限る（ステップ 9）。

## 能力のレッドライン（公式ソースで検証済み、2026-10-24）

登録表の全文は本リポジトリの `docs/CAPABILITIES.ja.md`（能力アトミックレジストリ。条目番号は C#### の形で引用する）。以下を超える設計はしない。

- **視線トラッキングはない**: ここでいう「視線」とは、カメラ画角の中心と頭部の向き（`AbsoluteOrientationSensor`）の組み合わせを指す。頭部が静止したことの判定には `onOrientationStabilityChange` を、うなずきの判定には `onHeadGesture('nod')` を使う。
- **OCR 用の API はない**: 文字を読む処理は「カメラで撮影し、LLM に画像として渡す」形で実装する。撮影は `ImageCapture.takePhoto` で行い、モードは `telephoto`（遠くの小さな文字、2016×1512）、`wide`（バーコードや広い画角、2016×2688）、`default`（3024×4032）の 3 つ。バーコードの読み取りには標準の `BarcodeDetector` を使う。
- **マイクモード**: AIUI のマイク API でのみ切り替えられる。値は `wearer`（デフォルト）/ `far-field` / `near-field` / `omnidirectional` の 4 つと、`system-audio`。wx のレコーダーからはモードを指定できない。
- **権限（パーミッション）**: 名前は次の 7 つだけが存在し、大文字・小文字も区別される（出典: `1-framework/open-agent-format/app-json.md`）。端末機能用が `GEOLOCATION`、`CAMERA`、`RECORD_AUDIO`、システムのメディアライブラリ用が `READ_MEDIA_IMAGES`、`CREATE_MEDIA_IMAGES`、`READ_MEDIA_AUDIO`、`CREATE_MEDIA_AUDIO`。表にない文字列を書いても権限は得られない。また、宣言しただけではシステムの許可が下りたことにはならない。拒否された場合や利用できない場合は、呼び出し側で必ず対処する。ASR 用の権限は別に存在しない（旧 `SPEECH_RECOGNITION` は Ink 0.19 で削除された）。
- **ディスプレイ**: 単色グリーン。ランタイムのキャンバス 480×352 に合わせて設計する。
- **LLM**: ホスト側で管理される `LanguageModel` のストリーミングのみ。ツール呼び出しは `toolcall` イベントとして届くだけで、自動実行はされない。**TTS**: 音声は固定 11 種類。`lang` 属性を指定しても効かない。
- **ネットワーク**: HTTPS のみ利用でき、ドメインは事前に申請した許可リストに載っている必要がある。LAN への直接接続はできない。通信がスマートフォンアプリ経由で Bluetooth 中継される場合がある。
- **ランタイム**: QuickJS（2024-01-13）+ Skia。ES2023 にフル対応し、モジュールは **ESM のみ**。CommonJS の `require()` は使えず、トップレベル await も使えない。使える API はブラウザの流儀ではなく、公式ドキュメントに列挙されたものに限られる。リファレンスに載っていない API は、この環境には存在しないものとして扱う（後述の API 規律と、本スキルと同じフォルダにある `API-AUDIT.md` を参照）。

- **音声対話は MVP 後に回す（GO、2026-10-24）**: Rokid AIUI Agent は音声対話（ASR による入力と TTS による応答）に対応している。一方、現行フリートの設計は操作とジェスチャに寄りすぎている、というのが GO の指摘である。音声を主チャネルに据える改修（音声での入力と命令、音声での確認と訂正、TTS によるフィードバック）は、現在の MVP が終わるまで着手しない。稼働中の設計を今の段階で変えないこと。この改修は、下記の UI 統一とあわせて MVP 後の「対話の定義」フェーズで扱う。

- **ジェスチャ優先、ボタンは最小限に（GO、2026-10-24）**: 主な操作デバイスはテンプル（つる）のタッチパッドである。タップ = 確認（`Enter`）、ダブルタップ = 戻る（`Backspace`）、スワイプ = スクロール／切り替え（`ArrowUp/Down`）、頭部の静止 + うなずき = 視線による確定、という割り当てを基本とする。1 本指の長押しでアシスタントが起動し、2 本指の長押しで AI ショートカット命令（最大 500 文字の固定テキストを指定した Agent に送る仕組み。ASR を一切通らないハードウェア側の入口）が発動する。検証済みのジェスチャ一覧は、能力レジストリの C8002–C8010 を参照。ページはジェスチャだけで主フローが完結するように設計し、画面内のボタンは最小限にとどめる。各 Agent のジェスチャ割り当ては README に明記する。（ボタン様式のばらつきをそろえるフリート全体の UI 統一は、全 120 件がそろうまで GO の判断で意図的に先送りされている。先回りして着手しない。）

実在する API に結線できない機能は、サンプル／プレースホルダーである旨と、未接続の接続先を、UI と README の両方に正直に書く（gaze-translate の書き方を参照）。できもしない能力をあるかのように見せない。

- **現在のフェーズは MVP（GO、2026-10-24）**: まずは機能として正しく動く Agent を出す段階であり、UI の磨き込みや対話の工夫を今から盛り込む段階ではない。対話モデルと UI 統一の設計は、GO が MVP フリートを実機でテストした後に行う。対話のあり方は、テスト結果から決めるものだからである。

## 製作の教訓（JP/KR シリーズ修正における GO の裁定、2026-10-25）

- **ローカライズ版の言語純度**: ユーザーに見える文字列はすべて、最初からその Agent の現地言語で書く。対象はステータス、ヒーロー表示、行、マーク、ガイド、TTS のセリフ、SCAN のプロンプト、シードデータ／デモデータまで含む。英語のまま残してよいのは英語のクローム部分（ページタイトル、ボタンラベル、`EVT:` プレフィックス）だけ。README も Agent 自身の言語で書く（後述のリポジトリ言語ルールを参照）。ほかの地域向けの文字列をコピーして UI を作らない。JP/KR のジェネレーターはこの方法で、日本語版に韓国語 UI をそのまま載せて出荷した前例がある。検証はパッケージング前に機械的に行う。KR 版は、UI 文字列に仮名が 0 件かつ CJK 表意文字が 0 件であること。JP 版は、中国語でしか使わない言い回しが混ざっていないこと（ガイド文と SCAN のプロンプトが典型的な混入箇所）。チェックはソースだけでなく、ビルド後のファイルに対してもかける。
- **配色はグリーン系のみ**: CSS で使う色はグリーンの階調に限る。`#ffffff` と白の `rgba(255,255,255,…)` は禁止。プレビューでは CSS の色がそのまま描画されるため白く見えるが、実機の単色グリーンパネルでは輝度に応じてグリーンに割り当てられる。したがって明暗はグリーンの濃淡で直接表し、「白」の役割には最も明るいグリーン `#7dff9e` を使う。スクリーンショット撮影のパイプラインでは、プレビュー画面の背景を黒で塗り、キャンバス四隅の角丸部分（透明）が白く見えないようにしている。
- **ボタンの見た目は UI の形に合わせる**: Agent をまたいで使い回す共通のデフォルトボタンは作らない。UI の形態ごとに、形・枠線・塗り方を含め、その Agent の世界観の一部として読めるボタンスタイルを設計する。唯一の例外が DEMO ボタンで、撮影パイプラインのクリック位置に合わせてジオメトリ（位置と大きさ）だけは固定されているため、変更できるのは外観のみとする。
- **環境の常識ゲート（コンセプト段階で確認）**: 舞台は、人がふだん眼鏡をかける場所から選ぶ。通勤、食事、買い物、自宅、屋外、社交の場面が想定範囲。入浴・蒸気・高温の環境（温泉 / チムジルバン / サウナ）は対象外とする。眼鏡をかける人がいないうえ、施設側が電子機器の持ち込みを禁じていることが多く、蒸気や熱で端末自体も傷むためである。出荷済みのコンセプトが後からこの観点で不適格と分かった場合は、その場で退役扱いにする（ディレクトリ、ブランチ、README は残し、退役した旨を注記する。削除はしない）。同じ番号の枠に代替の Agent を入れ、一覧同期 cron 側にもガードを入れて、退役した slug が一覧に再び載らないようにする。
- **再生成すると後処理が消える点に注意**: ジェネレーターで再ビルドすると、README と package.json は仕様から作り直されるため、バージョンの引き上げや変更履歴の追記といった手作業の後処理は消えてしまう。パッケージングは、README とバージョンが確定した後に、最後に行う。再生成した場合は、バージョン引き上げと変更履歴を入れ直してから、push の前に必ず確認する（package.json と README のバージョン表記、パッケージの中身）。
- **リポジトリの言語ルール（GO、2026-10-29）**: リポジトリは 1 つに保ち、言語ごとに分割しない。ファサード文書（ルート README、`ERROR-CODES.md`、カテゴリ別 README、自作の skills 文書、`mcp/README.md`、`docs/CAPABILITIES.md`、`docs/STORAGE.md`）は 3 言語でそろえる。中国語版を正本として所定の場所に置き、英語版と日本語版を `<name>.en.md` / `<name>.ja.md` として並べる。各言語版とも H1 の直後に言語切り替え行を置き、翻訳版には、準拠した中文版の版と日付を明記する（解釈に相違がある場合は中文版を正とする）。上流の aiui-dev 文書は翻訳対象に含めない。Agent ごとの README は、その Agent の言語による単一言語で書く。中国語の Agent は中国語、`japan/` の Agent は日本語、`korea/` の Agent は韓国語で、審査提出のセクションも同じ言語で統一する。Studio インポートブロックの案内文は README の言語に合わせ、URL ブロックそのものは変更しない。コードやシステム文言の引用など、逐語で残すべきリテラルは原文のままにする。ルート README の「標準ワークフロー」の節と、文字を含む画像にも同じルールを適用する。ワークフロー図とバッジは言語ごとに 1 ファイルを用意し（`assets/workflow.en.svg` / `assets/workflow.ja.svg`、`assets/badges/badge-*.en.svg` / `*.ja.svg`、各言語版の行内 shields ラベル）、変更するときは 3 言語を同じ変更の中でそろえて更新する。中国語だけを先に直して翻訳を後回しにしない。翻訳の書き方についても決まりがある。中国語を一文ずつ置き換えるのではなく、対象言語の開発者が日常使う言い回しで書くこと（GO、2026-10-29）。目標は、その言語の開発者が同じ文書をゼロから書いたときの姿であり、用語、文体、文書の構成はいずれもその言語の開発コミュニティの慣行に合わせる。そのうえで、事実、コード、数値、構造上の不変条件は中文の正本と完全に一致させる。
- **全体エラーコード（GO、2026-10-28）**: Agent の失敗箇所はすべて、フリート共通のエラーコード表（リポジトリ直下の `ERROR-CODES.md`）に対応づける。新しいコードの割り当てはレジストリ側でのみ行い、開発者が勝手に採番しない（運用ルールはコード表のガバナンスの節を参照）。表記は裸のコード（`E####`、例: `E2005`）のみとし、これ以外の形は使わない。コードの定義箇所、グラス側の表示、TTS の読み上げ、`lastError` への保存（対象 Agent の slug とバージョンもあわせて記録）、デバッグ時の表記まで、すべてこの形で統一する。接頭辞は一切付けない。数字部分だけでフリート全体で一意になる設計であり、シリーズ名や Agent 名を接頭辞にする方式は試行のうえで GO が 2026-10-28 に廃止した。Agent が最後に起こしたエラーは、完全なコード、slug、バージョン、元のエラーメッセージをそろえて `lastError` に残す。README には「错误码」の節を設け、その Agent が出しうるコードを列挙する。なお、`FileReader` は Ink ランタイムには存在しない。Blob を dataURL に変換する場合は `blob.arrayBuffer()` で読み、`btoa` をチャンク単位にかける形で実装する（フリートで最初に報告された現場事例が、AV11 で発生した E2005 である）。
- **API 規律 — 公式リストに載っているものだけを使う（GO、2026-10-29）**: このルールは、AV11 が公式リファレンスに載っていない `FileReader` を使ったコードを出荷し、その問題が実機で初めて表面化した件を受けて設けた。監査の全文は、本スキルと同じフォルダにある `API-AUDIT.md` にある（公式の `documentation/` と aiui-dev の references を 2026-10-29 にすべて読み通した結果）。以下は新規 Agent すべてに適用する。
  1. **出典をたどれる API だけを使う**: Agent が呼び出す API はすべて、公式リファレンス（aiui-dev の `references/apis/`、または上流の `documentation/3-api/`）に、文書化されたシグネチャ付きで載っていることを確認する。ブラウザや MDN、Web Speech、WeChat ミニプログラムで見慣れていることは、この環境にその API がある根拠にはならない。ドキュメントの該当項目を具体的に指せない API は使わない。例外は認めず、「たぶんあるはず」で通すこともしない。
  2. **「不在リスト」は使用禁止**（公式ドキュメント全体を調べて 1 件も見つからなかったもの、および非対応と明記されたもの）: `FileReader`、`sessionStorage`、`XMLHttpRequest`、`URL.createObjectURL`、`DOMParser`、`structuredClone`、`queueMicrotask`、`Notification`、クリップボード系 API、`IntersectionObserver`、`MutationObserver`、`ServiceWorker`、`new Worker()`、`canvas.toDataURL()`、`canvas.toBlob()`、`canvas.captureStream()`、WebGL、`OffscreenCanvas`、`getDisplayMedia`、`track.applyConstraints()`、`getPhotoCapabilities()/getPhotoSettings()`、`TextDetector`/`FaceDetector`（OCR 用 API は存在しない）、DOM 式の `onclick=` ハンドラ、`App()`/`Page()`/`Widget()` の登録呼び出し、`speechSynthesis.getVoices()`、TTS の cancel / pause / resume、`navigator.permissions`、Web Crypto の暗号化・復号と RSA / ECDSA / JWK。静的チェックではこの一覧を grep し、1 件でも一致したらビルド不合格とする。
  3. **Ink のバージョン要件を確認する**: API はランタイムのバージョンごとに追加されてきた（0.15 でセンサー、0.17 でメディアキャプチャと OPFS、0.18 で Widget / Agent Worker / Web Audio / ジオロケーション、0.19 で `convertToBlob` / `createImageBlob`。対応表の全文は `API-AUDIT.md` にある）。設計時は `app.json.engine` の下限バージョンを基準にし、バージョン依存の API やホスト側で任意提供の API には存在チェックのガードを入れる（`typeof` によるチェック、公式 TTS チュートリアル自体が採る方式、または `wx.canIUse()`）。ただし、このチェックで分かるのはインターフェースの存在だけで、端末が実際に実行できることや、ユーザーが許可済みであることまで保証するものではない。
  4. **文書化された使い方から外れない**: リストに載っている API でも、使えるのは文書化された形式だけである。`MediaRecorder` が受け付ける MIME 文字列は文書にある 4 種類のみで、`isTypeSupported` は静的メソッドとしてのみ使う。マイクモードを指定できるのは `getUserMedia` の音声制約の中だけであり、ASR や wx レコーダーには持ち込めない。`promptStreaming` は WHATWG 標準のストリームではなく、`read()` でポーリングするオブジェクトである。`LanguageModel.availability()` の戻り値は `available` と `unavailable` のどちらかだけで、中間の状態はない。センサーの値は、最初の読み取りが来るまでは `null` である。ASR の `error` カテゴリ文字列には公式の列挙定義がないため、MDN の Web Speech のエラー名を根拠に分岐を書かない。実機で確認済みの値でない限り、汎用のエラーコードで処理する。
  5. **wx はサブセットとして扱う**: wx 互換 API の対象範囲は `weixin-compatible-apis.md` に列挙されたものだけ。WeChat の API を記憶を頼りに持ち込まない。

- **バッジの定義は凍結中**: ルート README のシリーズバッジは次の 5 種類のみ（指向性 / 注意力 / 路缘坡 / 游戏 / 影视听）。GO の明示的な指示がない限り、バッジの追加や定義変更はしない（影视听 は AV のオーディオビジュアル系シリーズ向けに、GO が 2026-10-28 に追加したもの。shields の色は E91E63、凡例の SVG は `assets/badges/badge-av.svg`）。これら 5 シリーズに属さない Agent に既存のバッジを付けられるのは、そのシリーズに機能面で実際に属している場合だけであり、無理に付けない（JP/KR の帰属対応表は MEMORY を参照）。

## 手順

1. **設計**: 扱う生活上の課題を 1 つ定め、指向性のコア（GAZE / HEAD / MIC4 / GEO-H / SCAN）と、使う API を正確に挙げる。各 API は公式リファレンスの該当項目まで出典をたどる（前述の API 規律）。着手前にレッドラインを確認し、標準機能との競合チェック（Agent の中核が「標準機能 + 小さな工夫」で終わっていないか）と、前述の環境の常識ゲートを通す。
2. **開発**: 作業場所は `<slug>/`（app.json、AGENTS.md、app.js、pages/*.ink）。プロジェクト直下には `.aixignore` を置き、`.agents/`、`.aix/`、`artifacts/`、`*.aix`、`skills-lock.json`、`node_modules/` を除外する。
3. **静的チェック**: app.json の JSON パース、JavaScript の構文チェック、権限の宣言が実際に使う機能と一致しているか（権限名は 7 種類の表にあるものだけ）を確認する。API 規律のチェックとして、ビルド後のファイルに対して不在リストの一括 grep（前述の API 規律、ルール 2）に加え、旧来のパターンである `Page(`、`App(`、`Widget(`、`require(`、`onclick=` と、旧形式の `workers` フィールドも grep し、1 件でも一致したら不合格とする。自明でない API 呼び出しは、すべて公式リファレンスまで出典をたどれること。Canvas のコードは、描画後に `ctx.flush()` を呼ぶこと。エラーコードの結線も確認する。失敗箇所はすべて全体エラーコード（リポジトリ直下の `ERROR-CODES.md`）の裸の `E####` 形式に対応づけ、元のエラーメッセージをそのままユーザーに見せない。`FileReader` がコードのどこにも含まれていないことも確認する（Ink ランタイムには存在しない）。ローカライズ版では、ビルド後のファイルに対して言語純度のチェックも行う（前述の製作の教訓を参照）。このステップに加えて、公式 aiui-dev の `checklist.md`（§6 の API チェック、§8 の実行による検証、§9 の 3 段階の完了報告）も適用する。
4. **パッケージング**: `aix pack . -o <slug>.aix` で作成し、サイズを記録する。サイズが突然大きく跳ねた場合は、`.aixignore` の設定が壊れているサインとして扱う。
5. **プレビュー**: ローカルのプレビューパイプライン（スキル `rokid-preview-screenshots`）で全ページのスクリーンショットを撮影し、リポジトリ直下の `screenshots/<slug>/` に保存する。
6. **README**: 先頭（H1 タイトルの直後）に、コピーすればそのまま使える Studio インポートブロックを必ず置く。置き方は、「**Studio 导入地址**（复制到 Global AIUI Studio 的 Import Project 输入框）：」の 1 行に続けて、`https://github.com/sakai55/rokid/tree/agent-<slug>` だけを書いたコードブロック（フェンス付き）を置く形とする（GO、2026-10-24）。ブランチ側に置く README のコピーでも、先頭のブロックは同じにする。インポートブロックの直後には、AIX の直接ダウンロード行を、README 自身の言語で書く。最新版であることを示す太字のラベルを付け、Markdown リンク `[<slug>.aix](https://raw.githubusercontent.com/sakai55/rokid/main/aix/<slug>.aix)` の形で示す（GO、2026-10-29）。これにより、最新パッケージは `aix/` の中を探し回らなくても README からワンクリックで開ける。この行は main とブランチの両方に置く。例外は MUD プロジェクトのフォルダで、こちらは専用の `MUD/aix/` を使うため対象外とする。README 本体には、機能の説明、指向性の使い方、権限の一覧、パッケージングとプレビューのコマンド、実機テスト情報の表（Studio 名 / Version / Category / Intent / Agent ID / 状態。Studio へのインポート後に埋める）、「错误码」の節（その Agent が出しうる全体コードを `E2005` のような裸の形式で列挙し、報告時の約束事もあわせて書く）、`../../screenshots/<slug>/*.png` を埋め込んだ「预览截图」の節（Agent の置き場所は 2 階層下の `<分类>/<slug>/` である）、そして区切りを明示した「提审资料 (Review Submission)」の節を含める。提审资料 の内訳は、Feature Description（500 文字以内）、Opening Message（500 文字以内、Markdown）、Preview Media（3–5 ファイル、画像 1 件以上と動画 1 件以上を含む。動画は実機テストの段階で埋める）、Build ごとに Features added / Improvements / Fixes に分けた Change Log である。
7. **GitHub への同期**: 端末の `git` / `gh` で行う（sakai55 でログイン済み。GitHub の操作は事前承認済み）。main への push 先は `<分类>/<slug>/`（分類フォルダは ID の頭文字で決まる。DI→directional、WA→watch、HO→hold、CO→cover、FI→filter、DU→dual、RE→review、CU→cue、SO→social、BO→body、AM→ambient、CC→curb-cut、GA→games、番号なしは base）。パッケージは `aix/<slug>.aix` に、スクリーンショットは `screenshots/<slug>/` に置き、同じファイル一式をブランチ `agent-<slug>` の**ブランチ直下**にもそろえる（ブランチ直下がそのままプロジェクト直下になる。サブディレクトリへのコピーや、余分な .aix ファイルを置かないよう、ブランチ内はきれいに保つ）。
8. **登録**: 50 件の PLAN の進捗表で対象 Agent を ✅ とし、AIX のサイズ、スクリーンショット数、ブランチ名を記録する。ルート README の Agent 一覧は、専用の cron では保守しない（`rokid-agent-list-sync` cron は 2026-10-26 に廃止済み）。現在は、日次の精品ラインの実行が、その日のバッチを push した後に 1 回だけ、一覧の先頭に新しい行を追加する形になっている（一覧は Studio インポートの節の直後にあり、2026-10-28 以降は新しい順に並ぶ。末尾への追加はしない）。この実行以外で、一覧を手作業で編集しない。
9. **実機テストと提出（GO の指示があった場合のみ）**: GO が Global Studio で `tree/agent-<slug>` からインポートし、Device Debug → Package and Save を実行する。Hi Rokid 側でグラスのリソースパッケージが更新されたら、音声で Agent を起動して確認する。審査への提出は、GO が「真机测试完成了」と言った場合にのみ行う。提出時は README の「提审资料」をそのまま貼り付け、提出後に実機テスト情報の表を埋める。
