# Rokid Agent Production SOP
[中文](SKILL.md) | [English](SKILL.en.md) | 日本語
中文版（2026-10-29 時点）からの翻訳。齟齬がある場合は中文版が優先する。

Agent 1 件 = 完全なシナリオ 1 つ（下記の基本ルールを参照。旧来の「生活上の問題 1 つ」という捉え方より優先する）。9 ステップをすべて踏むこと。ステップ 8 で登録が済むまで、その Agent は完成ではない。

## 基本ルール — Agent 1 件につき完全なシナリオ 1 つ（GO、2026-10-26）

Rokid 公式開発チームが本リポジトリをレビューし、海外 Agent Store の全カタログ（約 32 件）を分析した結果を受けて定めた。**作るのは「Agent 1 件につき完全なシナリオ 1 つ」だけであり、「Agent 1 件につき機能点 1 つ」は決して作らない。** 旧フリートの形状に対する公式の見解は次のとおりである。その程度に小さい機能は基本的に審査を通らず、Agent 1 件に小さい点 1 つではおそらく 1 件も通らない。薄いシナリオは、公開後にシステム側の禁止措置や利用者からの苦情を受けるおそれがある。ストアで生き残っているものが基準を裏付けている。完全なプレイ循環を持つ完成したゲーム、1 つのハブ配下の集合（ストアで利用数 2 位はミニゲーム集合）、日常の意思決定シナリオ（今日何を食べるか／何を着るか／どう鍛えるか）、実データに基づくサービス、コンテンツ集合であり、単一の動作だけのものは決してない。

コンセプトは、ステップ 1 の設計作業を始める前に、次の 3 つの関門をすべて通過しなければならない。どれか 1 つでも落ちれば、その場でコンセプトは却下する（「まず作ってみてから考える」はしない）。

1. **シナリオ関門。** 誰が、どの瞬間に、何を成し遂げるために開くのかを一文で言えること。動作や機能ではなく、瞬間と課題であること。シナリオを言い表せないなら作らない。
2. **循環関門。** 入口 → 過程 → 結果／決済という完全な循環があり、繰り返し使えること。単一動作、単一ページ、単一プロンプトの Agent は不合格。ゲームだけが唯一の緩和であり（ストアで実証済み）、単一の仕組みが許されるのは完全なプレイ循環（開始、勝敗、得点）がある場合に限る。
3. **厚み関門。** 実データソース、コンテンツ集合、複数ステップの流れ、セッションをまたぐ記憶、集合ハブのうち、少なくとも 2 つを持つこと。組み込み機能と同体であるものは即不合格（衝突監査の第 1 区分であり、組み直さない、提出しない）。

実行ルール:

- **既存フリート（170 件超の薄い Agent）。** 1 件ずつ提出しない。削除もしない。シナリオ単位で組み直す。1 つのシナリオの単点 Agent 群を 1 つのシナリオ Agent に統合し、統合できないものはリポジトリ内に封存したまま残す。
- **提出順序。** 最初の提出は、関門を通過した見本だけに限る。(1) 頭部ゲーム集合ハブ。すべてのゲームを含む単体の Agent 1 件である（Agent 同士は呼び出せないため、ハブとはゲームを内包した単一の Agent であり、ルーターではない）。(2) dabiaoge。見本が 1 件通り、実際の基準が分かるまでは、それ以外を審査に出さない。
- **量産 — 2026-10-26 22:49 に統一精品ラインへ置き換え。** 旧来の毎日バッチ cron 3 本（curb-cut / JP-KR / head-games、各 3 件/日）は廃止した。代わりに cron `rokid-boutique-daily-10` を 1 本だけ走らせ、納品先はサイドチャット「做的就是精品」のみとする。5 方向（curb-cut（CC）、指向性、注意力、ゲーム（GA）、JP/KR ローカライズ）から 10 件/日。そのうちちょうど 5 件は「日本在地 × 複合」であり、日本の地域性を場面とする（JP 番号、`japan/`、日本語 UI）うえで、curb-cut / 指向性 / 注意力 / ゲームのうち少なくとも 2 方向と組み合わせる。日本の地域性だけ、または 1 方向だけとの組み合わせは不可。残り 5 件は自由な単一方向、または 2 方向以上の組み合わせとする。組み合わせはシナリオとして自然でなければならず、2 つの機能の寄せ集めは不可。旧 `rokid-agent-list-sync` cron（ルート README の Agent 一覧、6 時間ごと）も廃止した。精品ラインの実行が、その日のバッチをプッシュした後に 1 回だけ、ルート README の一覧を自ら更新する。下記のステップ 8 の注記と、MEMORY にある凍結済みバッジ／図例／退役済み slug のルールが、その締めのステップに適用される。すべてのコンセプトは先に 3 つの関門を通すこと。落ちたコンセプトは厚みを増やすか棄却し、その判定を報告する。件数を満たすために基準を下げることは決してしない（不足分はコンセプトごとの判定とともに報告する）。位置づけ（GO、2026-10-26 22:50）: 既存の 177 件は、可能性と能力の境界を探った探索フリートである。精品ラインはその上に収束し、検証済みの仕組みと教訓を再利用し、薄い「1 機能 1 Agent」という形状を再現することは決してない。頭部ゲーム集合ハブ（`head-games-hub`、GA27–GA40 は予約済みの仕組み）は上記のとおり提出見本のままであり、精品ラインが GO の指示なく、それらの予約済み GA 番号を単体ゲームに消費することはない。
- **実機テスト関門は不変。** 提出は、GO の実機テストが完了し、GO が「真机测试完成了」と言った後にのみ行う（ステップ 9）。

## 能力のレッドライン（公式ソースで検証済み、2026-10-24）

完全な登録表: 本リポジトリの `docs/CAPABILITIES.ja.md`（能力の原子登録表、条目は C#### で引用）。次を超える設計は決してしない。

- **視線追跡はない。** 「視線」とは、カメラ画角の中心 + 頭部方向（`AbsoluteOrientationSensor`）のことであり、頭を静止させた確認は `onOrientationStabilityChange`、うなずきによる確認は `onHeadGesture('nod')` で行う。
- **OCR API はない。** テキストを読むとは、カメラ撮影 + LLM の画像入力のことである。`ImageCapture.takePhoto` の撮影モードは `telephoto`（遠くの小さい文字、2016×1512）、`wide`（バーコード／広い範囲、2016×2688）、`default`（3024×4032）。バーコードはネイティブの `BarcodeDetector` を使う。
- **マイクモード** は AIUI マイク API 経由でのみ使える。`wearer`（既定）/ `far-field` / `near-field` / `omnidirectional`、および `system-audio`。wx レコーダーではモードを選べない。
- **権限**: 正確に 7 つの名前だけが存在し、大文字小文字を区別する（`1-framework/open-agent-format/app-json.md`）。デバイス能力向けの `GEOLOCATION`、`CAMERA`、`RECORD_AUDIO` と、システムのメディアライブラリへのアクセス向けの `READ_MEDIA_IMAGES`、`CREATE_MEDIA_IMAGES`、`READ_MEDIA_AUDIO`、`CREATE_MEDIA_AUDIO` である。認識されない文字列は何の権限も与えない。宣言はシステム側の許可ではないため、拒否や利用不可は呼び出し側で処理しなければならない。ASR に個別の権限はない（旧 `SPEECH_RECOGNITION` 権限は Ink 0.19 で削除された）。
- **表示**: 単色グリーン。480×352 のランタイムキャンバスに合わせて設計する。
- **LLM**: ホスト管理の `LanguageModel` ストリーミングのみ。ツール呼び出しは `toolcall` イベントとして届き、自動では実行されない。**TTS**: 固定 11 音声。`lang` 属性は効果を持たない。
- **ネットワーク**: HTTPS のみ。ドメインは申請済み許可リストに載っている必要がある。LAN への直接接続は不可。ネットワークは Bluetooth 経由でスマートフォンアプリを通して中継される場合がある。
- **ランタイム**: QuickJS（2024-01-13）+ Skia、ES2023 の完全対応、**ESM のみ**。CommonJS の `require()` は不可、トップレベルの await も不可。API の表面はブラウザのものではなく、文書に列挙された一覧である。API が公式リファレンスに載っていないなら、ここには存在しない（下記の API 規律の教訓と、本スキルの隣にある `API-AUDIT.md` を参照）。

- **音声対話 — MVP 後の調整（GO、2026-10-24）**: Rokid AIUI Agent は音声で対話できる（ASR 入力 + TTS 応答）。現行フリートの設計はすべて操作／ジェスチャ駆動だという指摘が GO からあった。音声対話の改修（主要チャネルとしての音声フロー。話した入力／命令、音声での確認／訂正、TTS フィードバック）は、現在の MVP が終わるまで延期する。稼働中の設計を今これのために変更しない。これは下記の UI 統一と同じく、MVP 後の対話定義フェーズに属する。

- **ジェスチャ優先、ボタンは最小限（GO、2026-10-24）**: テンプル（つる）のタッチパッドが主要なコントローラーである。タップ = 確認（`Enter`）、ダブルタップ = 戻る（`Backspace`）、スワイプ = スクロール／切り替え（`ArrowUp/Down`）、頭の静止 + うなずき = 視線確認。シングルフィンガーの長押しでアシスタントが起動し、2 本指の長押しで AI ショートカット指令（固定テキスト、500 文字以下、選んだ Agent へ届けられる。ASR を完全に迂回するハードウェア入口）が発火する。検証済みのジェスチャ表の完全版は能力登録表の条目 C8002–C8010。メインフローがジェスチャだけでも進むようページを設計し、画面上のボタンは最小限に抑え、その Agent のジェスチャ対応を README に明記する。（「似た様式のボタンが多すぎる」問題へのフリート全体の UI 統一は、全 120 件が終わるまで GO が意図的に延期している。早く着手しない。）

機能を実在の API に結線できない場合は、UI と README で、見本／プレースホルダーであることと、未接続の接続先の名前を正直に表示する（gaze-translate を参照）。能力を偽らない。

- **現在のフェーズ = MVP（GO、2026-10-24）**: 機能的に正しい Agent を出す。今は UI を磨いたり、対話の改良を発明したりしない。対話モデルと UI 統一は、GO が MVP フリートを実機テストした後にのみ設計する。テストこそが、対話がどうあるべきかを定めるからである。


## 製作の教訓（JP/KR シリーズ修正における GO の裁定、2026-10-25）

- **ローカライズ Agent の言語純度。** 利用者に見えるすべての文字列（状態、ヒーロー表示、行、マーク、ガイド、TTS の文、SCAN のプロンプト、シード／デモデータ）は、最初からその Agent の現地言語で書く。英語のまま残るのは英語の体裁部分だけである（ページタイトル、ボタンラベル、`EVT:` プレフィックス）。README のドキュメントは、その Agent 自身の言語で書く（下記のリポジトリ言語ルールを参照）。ある地域の UI を、別の地域の文字列をコピーして作っては決してならない。JP/KR ジェネレーターはこのやり方で、日本語版に韓国語 UI を丸ごと出荷したことがある。パッケージ化の前に機械検証する。KR ビルドでは UI 文字列中の仮名数 = 0 かつ CJK 表意文字数 = 0。JP ビルドでは、中国語にしかない言い回しがないこと（ガイドと SCAN プロンプトが通常の隠れ場所である）。走査はソースだけでなくビルド済みファイルに対して行う。
- **グリーンのみの配色。** CSS はグリーンの階調だけを使う。`#ffffff` と白い `rgba(255,255,255,…)` は禁止。プレビューは CSS の色をそのまま描く（白いスクリーンショットになる）が、実際の単色グリーンのパネルはすべてを輝度で割り当てる。したがって明暗はグリーンで直接表現し、最も明るいグリーン `#7dff9e` を「白」の役割に当てる。撮影パイプラインはプレビュー画面の背景を黒くし、キャンバスの角丸の透明部分が白く読まれることが決してないようにする。
- **ボタンは UI の形態に従う。** Agent をまたぐ共通の既定ボタンは使わない。UI の形態／アーキテクチャごとに、独自のボタンスタイルを持つ（形、枠線、塗りの考え方が、その Agent の比喩の一部として読めること）。唯一の例外は DEMO ボタンであり、その幾何形状は撮影パイプラインのクリック位置で固定されているため、表皮だけを変える。
- **環境の常識関門（コンセプト段階）。** 設定は、人が実際に眼鏡をかける場所でなければならない。通勤、食事、買い物、自宅、屋外、社交。入浴／蒸気／高温の環境（温泉 / チムジルバン / サウナ）は対象外である。そこでは誰も眼鏡をかけず、施設が電子機器を禁じ、蒸気や熱がデバイスを傷める。出荷済みのコンセプトが後からこの審査に落ちた場合は、その場で退役させる（ディレクトリ／ブランチ／README は残し、退役の注記を加え、決して削除しない）。同じ番号の枠内で代替品に置き換え、一覧同期 cron をガードして、退役済み slug が再び追加されることがないようにする。
- **再生成は後処理を消す。** ジェネレーターの再ビルドは、仕様から README と package.json を書き直すため、バージョン番号の引き上げや変更履歴のセクションが消える。パッケージ化は最後に行い、README とバージョンが確定した後に行う。再生成の後は必ず、バージョン引き上げ + 変更履歴を再適用し、プッシュ前に検証する（package.json と README でのバージョン検索、パッケージ内容）。
- **リポジトリ言語ルール（GO、2026-10-29）**：1 リポジトリとし、言語で分割しない。門面文書（ルート README、`ERROR-CODES.md`、カテゴリ README、自作 skills 文書、`mcp/README.md`、`docs/CAPABILITIES.md`）は 3 言語体制とする。中国語版が正本としてその場にあり、英語版と日本語版を `<name>.en.md` / `<name>.ja.md` として並置し、各版とも H1 の直後に言語切替行を置き、翻訳版には従った中文版の版／日付を明記する（齟齬がある場合は中文版が優先）。上流の aiui-dev 文書は翻訳しない。各 Agent 自身の README はその Agent の言語で単一言語とする。中国語 Agent は中国語、`japan/` の Agent は日本語、`korea/` の Agent は韓国語とし、審査提出セクションも含む。Studio 導入ブロックの案内文は README の言語に従い、URL ブロック自体は決して変えない。逐語リテラル（コード、引用されたシステム文言）はそのまま残す。
- **全体エラーコード（GO、2026-10-28）。** すべての Agent のすべての失敗点は、フリートのエラーコード表（リポジトリルートの `ERROR-CODES.md`）に対応付ける。新しいコードは登記所だけが割り当て、自分で取ることは決してない（表のガバナンス節を参照）。裸のコード（`E####`、例 `E2005`）が唯一の形式である。Agent のコード内で定義し、眼鏡に表示し、TTS で読み上げ、`lastError` に保存し（その Agent の slug + バージョンとともに）、デバッグでも使う。いかなるプレフィックスも付けない（数字部分だけで全体に一意であり、シリーズ／Agent のプレフィックスは試されたが、GO が 2026-10-28 に廃止した）。Agent の最後のエラー（完全なコード + slug + バージョン + 原文）は `lastError` に保存し、README には「错误码」のセクションを置いて、使用するコードを列挙する。`FileReader` は Ink ランタイムに存在しない。Blob から dataURL への変換は `blob.arrayBuffer()` + 分割した `btoa` で行う（フリート初の現場報告は AV11 からの E2005）。
- **API 規律 — 公式一覧のみ（GO、2026-10-29）。** AV11 が、公式リファレンスに一度も載っていない API `FileReader` を使うコードを出し、その見落としが実機で初めて発覚したことを受けて定めた。この教訓の背後にある完全な監査は、本スキルの隣にある `API-AUDIT.md` である（公式 `documentation/` + aiui-dev リファレンスを、2026-10-29 に端から端まで通読した）。ルールはすべての新規 Agent を拘束する。
  1. **たどれる場合にだけ使う。** Agent が呼ぶすべての API は、公式リファレンス（aiui-dev の `references/apis/`、または上流の `documentation/3-api/`）で、文書化されたシグネチャとともに見つけられなければならない。ブラウザ、MDN、Web Speech、WeChat ミニプログラムへの慣れは、ここに API がある証拠にはならない。ドキュメントの該当項目を指せないなら、その API は使わない。例外はなく、「たぶんある」もない。
  2. **不在一覧は全面的に禁止**（公式ドキュメント全体で 0 件と検証済み、または明示的に非対応）: `FileReader`、`sessionStorage`、`XMLHttpRequest`、`URL.createObjectURL`、`DOMParser`、`structuredClone`、`queueMicrotask`、`Notification`、クリップボード API 群、`IntersectionObserver`、`MutationObserver`、`ServiceWorker`、`new Worker()`、`canvas.toDataURL()`、`canvas.toBlob()`、`canvas.captureStream()`、WebGL、`OffscreenCanvas`、`getDisplayMedia`、`track.applyConstraints()`、`getPhotoCapabilities()/getPhotoSettings()`、`TextDetector`/`FaceDetector`（OCR API はない）、DOM 式の `onclick=` ハンドラー、`App()`/`Page()`/`Widget()` の登録呼び出し、`speechSynthesis.getVoices()` と TTS の cancel/pause/resume、`navigator.permissions`、Web Crypto の encrypt/decrypt と RSA/ECDSA/JWK。静的チェックはこれらを grep し、1 件でも当たればビルドは不合格。
  3. **Ink のバージョン下限に注意する。** API はランタイムのバージョンごとに到着した（0.15 センサー、0.17 メディア取得 + OPFS、0.18 Widget / Agent Worker / Web Audio / 地理位置、0.19 `convertToBlob`/`createImageBlob`。完全な表は `API-AUDIT.md`）。`app.json.engine` の下限に合わせて設計し、バージョン依存またはホスト側で任意の API には存在ガードを付ける（`typeof` チェック、公式 TTS チュートリアル自体のパターン、または `wx.canIUse()`。ただしこれはインターフェースの存在を証明するだけで、デバイスが対応できることや、利用者が許可したことを証明するものではない）。
  4. **文書化された形状のみ。** 一覧にある API でも、文書化された形式だけを使う。`MediaRecorder` は文書化されたちょうど 4 つの mime 文字列だけを取り、`isTypeSupported` は静的専用である。マイクモードは `getUserMedia` の音声制約の中にだけあり、ASR や wx レコーダーには決して入らない。`promptStreaming` は WHATWG のストリームではなく、ポーリングする `read()` オブジェクトである。`LanguageModel.availability()` はちょうど `available`/`unavailable` だけを返し、中間状態はない。センサーは最初の読み取り前は `null` を読む。ASR の `error` カテゴリ文字列には公式の列挙がないため、MDN の Web Speech のエラー名で分岐しては決してならない。値が実機で検証済みでない限り、汎用エラーコードに落とす。
  5. **wx はサブセットである。** wx 互換 API は `weixin-compatible-apis.md` が列挙するものだけを対象とする。記憶から WeChat API を持ち込んでは決してならない。

- **バッジの定義は凍結されている。** ルート README のシリーズバッジは 5 つだけである（指向性 / 注意力 / 路缘坡 / 游戏 / 影视听）。GO の明示的な指示なく、バッジの定義を追加・変更しては決してならない（影视听 は AV 影音シリーズ向けに GO が 2026-10-28 に追加した。shields の色は E91E63、図例 SVG は `assets/badges/badge-av.svg`）。それらのシリーズ外の Agent が既存のシリーズバッジを持つのは、そのシリーズに機能的に属する場合だけである。無理に付けない（JP/KR の帰属対応は MEMORY にある）。

## 手順

1. **設計** — 生活上の問題 1 つ。指向性の中核（GAZE / HEAD / MIC4 / GEO-H / SCAN）と、使う正確な API を名づけ、各 API を公式リファレンスの該当項目までたどる（API 規律の教訓）。先にレッドラインを確認し、デフォルト能力との衝突チェック（Agent の中核が、組み込み機能 + 小さなひねりであってはならない）と、上記の環境の常識関門を通す。
2. **開発** — `<slug>/` 内で行う（app.json + AGENTS.md + app.js + pages/*.ink）。プロジェクトルートには `.aixignore` を置き、`.agents/`、`.aix/`、`artifacts/`、`*.aix`、`skills-lock.json`、`node_modules/` を除外する。
3. **静的チェック** — app.json の JSON パース、JS の構文パース、権限が実際に使う機能と一致すること（名前は 7 つ表からのみ）。API 規律: ビルド済みファイルに対して、不在一覧の一括 grep（API 規律の教訓、ルール 2）と、古いパターン `Page(`、`App(`、`Widget(`、`require(`、`onclick=`、および旧 `workers` フィールドを grep し、1 件でも当たれば不合格。すべての自明でない API 呼び出しは、公式リファレンスまでたどれること。キャンバスのコードは描画後に `ctx.flush()` を呼ぶこと。エラーコード結線: すべての失敗点が全体エラーコード（リポジトリルートの `ERROR-CODES.md`）の裸の `E####` 形式に対応付き、裸の原文エラーが利用者に表面化せず、`FileReader` がどこにも現れないこと（Ink ランタイムに不在）。ローカライズ Agent では、ビルド済みファイルに対して言語純度の走査も行う（製作の教訓を参照）。公式 aiui-dev の `checklist.md`（§6 API チェック、§8 実行可能検証、§9 3 段階の完了報告）が、このステップの上に重ねて適用される。
4. **パッケージ化** — `aix pack . -o <slug>.aix`。サイズを記録する。パッケージが突然膨らんだら、`.aixignore` が壊れているということである。
5. **プレビュー** — ローカルのプレビューパイプライン（スキル `rokid-preview-screenshots`）で全ページのスクリーンショットを撮り、リポジトリルートの `screenshots/<slug>/` に保存する。
6. **README** — README の最上部（H1 タイトルの直後）には、コピーしてそのまま使える Studio インポートブロックを必ず置く。「**Studio 导入地址**（复制到 Global AIUI Studio 的 Import Project 输入框）：」という行に続けて、`https://github.com/sakai55/rokid/tree/agent-<slug>` だけを含むフェンス付きコードブロックを置く（GO、2026-10-24）。ブランチ側の README のコピーも、同じ最上部ブロックを保つ。README にはさらに次を含める。機能、指向性の使い方、権限、パッケージ化／プレビューのコマンド、実機テスト情報の表（Studio 名 / Version / Category / Intent / Agent ID / 状態。Studio へのインポート後に埋める）、「错误码」のセクション（この Agent が表面化しうる全体コードを `E2005` のような裸の形式で並べ、報告の約束事も書く）、`../../screenshots/<slug>/*.png` を埋め込む「预览截图」のセクション（Agent は現在 2 階層深い場所にある。`<分类>/<slug>/`）、そして区分された「提审资料 (Review Submission)」。その内訳は Feature Description（500 文字以下）、Opening Message（500 以下、Markdown）、Preview Media（3–5 ファイル、画像 1 件以上 + 動画 1 件以上。動画は実機段階で埋める）、Build ごとに Features added / Improvements / Fixes に分けた Change Log である。
7. **GitHub 同期** — ターミナルの `git`/`gh` 経由で行う（sakai55 としてログイン済み。GitHub 操作は事前承認済み）。main へは `<分类>/<slug>/` にプッシュする（分類フォルダは ID の頭文字による。DI→directional、WA→watch、HO→hold、CO→cover、FI→filter、DU→dual、RE→review、CU→cue、SO→social、BO→body、AM→ambient、CC→curb-cut、GA→games、番号なし→base）。`aix/<slug>.aix` をリポジトリに置き、スクリーンショットは `screenshots/<slug>/` へ置き、同じファイル一式をブランチ `agent-<slug>` の**ブランチルート**にミラーする（ブランチルート = プロジェクトルート。きれいに保ち、サブディレクトリのコピーや余分な .aix を置かない）。
8. **登録** — 50 件 PLAN の進捗表で、その Agent を ✅ にし、AIX サイズ、スクリーンショット数、ブランチ名を記す。ルート README の Agent 一覧は、もはや別の cron では保守しない（`rokid-agent-list-sync` cron は 2026-10-26 に廃止）。それ以降は、毎日の精品ラインの実行が、その日のバッチをプッシュした後に 1 回だけ、一覧の先頭に新しい行を追加する（一覧は Studio インポートのセクションの直後にあり、2026-10-28 以降は新しい順である。末尾へ追加しては決してならない）。その実行以外では、一覧を手作業で編集しない。
9. **実機テストと提出（GO の発動時のみ）** — GO が Global Studio で `tree/agent-<slug>` 経由でインポートし、Device Debug → Package and Save を行い、Hi Rokid が眼鏡のリソースパッケージを更新し、音声で Agent を開く。GO が「真机测试完成了」と言った場合にのみ、Studio で審査に提出してよく、README の「提审资料」をそのまま貼り、その後、実機テストの表を埋める。
